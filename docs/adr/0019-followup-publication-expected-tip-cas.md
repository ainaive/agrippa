# ADR-0019: Follow-Up Publication — the Expected-Tip CAS

- Status: accepted · Date: 2026-08-16
- **Amends ADR-0012**: the publish compare-and-swap generalizes from *creation* ("the tip is absent, or already this exact commit") to *tip advance* ("…or is the tip this chain last published"). Closes the deferral recorded in ADR-0018's Consequences. Builds on ADR-0017's publication inversion — publication stays server-side, on the server-pinned base, and this ADR requires **zero daemon changes**. Charted as Track P of [docs/plan/m3-plan.md](../plan/m3-plan.md).

## Context

ADR-0018 made a follow-up a new run that inherits its ancestor's workspace and session — and deliberately stopped short of letting it publish. The refusal it ran into is not an accident of implementation: ADR-0012's push is a creation CAS, and that refusal is the idempotency anchor that makes a lost push response reproduce a byte-identical commit instead of a duplicate. A follow-up breaks the creation assumption legitimately — it wants to advance a tip its own chain published — so publication needs a semantics change, not a workaround, which is why ADR-0018 deferred it here rather than absorbing it.

Two facts already true of the system make the change small:

- **Evidence is cumulative against a base that never moves.** The chain's clone base — sidecar-anchored for central runs, server-pinned `runs.workspace_ref` for daemon runs — is fixed at the ancestor's checkout and inherited verbatim (ADR-0018 Decision 2). A follow-up's approved patch therefore already contains its ancestors' changes, and applying it to the base tree yields the full intended tree. Advancing the tip is a *parent-selection* problem, not a rebase problem.
- **The snapshot commit is fully deterministic** given the base and the patch (ADR-0012 Decision 3, re-derived without the sidecar ref in the 0017 amendment). Adding one more input — the expected parent — preserves that: the commit SHA is a pure function of (base, patch, expected tip), which is what keeps retries idempotent across every crash window.

What is *not* acceptable is silently overwriting a tip the platform does not recognize: a human may have pushed to the delivery branch between runs, and their work must win by default.

## Decision

**1. Publication carries an expected tip, and the push is a CAS against it.** Every publish for a workspace chain computes an expected tip **E**: the snapshot commit this chain last published, or absent for a first publish. Commit construction: tree **T** = the approved cumulative patch applied to the base **B**'s tree (unchanged from ADR-0012); parent = **E** if present, else **B**; author/committer identity, message, and both dates pinned to B's commit as today — so the commit **C** is fully deterministic given (B, patch, E). The push then admits exactly three outcomes: the observed remote tip **is C** → idempotent success (a retry of a push whose response was lost); the observed tip **is E** → advance via `--force-with-lease=<ref>:E`; anything else → a typed `tip_conflict`, and the remote is never overwritten. A no-op guard runs first: if T equals E's tree, publication returns E without pushing — a steer that changed nothing must not mint an empty tip advance.

**2. The chain's publication record is a column, written where the work happens.** `runs.published_sha` (text, nullable, additive migration), written by the engine inside the `git.push` step handler immediately after the push resolves — the same pattern as `runs.work_branch` at `git.branch`. E for a chain = the latest non-null `published_sha` across the `workspace_key` group, ordered by run number. The crash window is self-healing by construction: a crash between push and record re-runs the step on resume, the push finds tip == C and succeeds idempotently, and the record lands. A chain whose ancestor pushed *before* this column existed derives E = absent and fails with a clean `tip_conflict`; the exposure window is one retention hour after deploy, and we accept it rather than build a recompute fallback (see Alternatives).

**3. A follow-up that changed the workspace publishes through a synthetic tail, and the tail is always approval-gated.** `followupTemplate` appends a `publish` phase only when all of: the base template contains a `git.push` system step, the base declares a workspace, the seed found a patch artifact key, and the chain has a `work_branch`. The tail is: an approval checkpoint presenting the cumulative patch (`onTimeout: cancel`) → system `git.push` → system `pr.open` *iff* the base flow had one (the provider adapters already recover an existing PR idempotently, so a chained follow-up re-targets the same PR). The checkpoint is unconditional by decision, not inherited from the base flow: ADR-0012's thesis is that *a human approves those bytes*, and the ancestor's approval covered the ancestor's bytes — a steering message is post-hoc to it. Even a base flow that auto-published does not exempt its follow-ups. The engine computes a tail guard the template language never sees: when the steer's stored patch is empty, or byte-identical (store-time digest) to the chain's last *approved* patch, the whole tail is skipped — nothing new to approve, nothing to publish. The existing evidence-drift guard (approved patch vs. live workspace diff) applies to the tail unchanged, on both transports.

**4. A conflict is a typed run failure, never an overwrite and never a retry loop.** `tip_conflict` from the push maps to a `publish_conflict` run failure — terminal, notified through the standard pipeline, with the branch and PR untouched. A retry deterministically reproduces the refusal, which is the point: the platform's view of the chain has diverged from the remote (most likely a human pushed to the branch), and reconciliation is a human decision. The recovery paths are ordinary ones — push the branch manually, or submit a fresh task from the current remote state.

**5. Publication remains the server's business, entirely.** The daemon's role ends where it ended in ADR-0017: it uploads the digested evidence patch. Base resolution, expected-tip derivation, commit construction, and the credentialed push all happen in the server's pristine temp repository. No daemon upgrade is required for this feature, and no daemon — current or stale — can influence which commit gets published beyond the bytes the human approved.

## Alternatives considered

- **Advance the base per follow-up (a rebase model).** Each follow-up would re-pin its base to the ancestor's published commit and carry an incremental patch. Rejected: cumulative evidence against an immobile base is what lets the approval checkpoint present *the whole delivered change*, keeps `applyApprovedPatch` a pure function of pinned inputs, and — per the 0017 amendment — a moving, daemon-visible base reopens exactly the smuggling ambiguity ("a patch can apply cleanly on many bases") that the server pin closed.
- **A tip-advance lease table or advisory lock.** Rejected as a second concurrency primitive solving an already-solved problem: the deterministic commit plus `--force-with-lease` plus the `published_sha` record *is* a compare-and-swap, and the ADR-0017 execution lease already serializes the chain's runs (`WorkspaceBusyError` queues concurrent follow-ups behind one another).
- **Skip the checkpoint when the base flow auto-published.** Rejected by Decision 3's rationale; recorded because it is the shape a future "trusted automation" feature would want — if that ever lands, it should arrive as its own reviewed decision, not as an inherited default.
- **A recompute fallback for pre-ADR chains** (rebuild the ancestor's commit from its stored approved patch to validate an unrecorded observed tip). Rejected: permanent complexity to shorten a one-retention-hour window that closes by itself.

## Consequences

- A chain publishes at most one new deterministic commit per approved steer; chained follow-ups advance E repeatedly, and the delivered branch reads as one platform-authored commit per approval — local agent history stays unpublished, as before.
- A human pushing to the delivery branch mid-chain wins by default: the next follow-up publish fails `publish_conflict` rather than overwriting. This is a feature with a cost — operators steering a branch they also edit by hand will see typed failures and must reconcile manually.
- `PushResult` gains `tip_conflict`, and `FakeScmService` must be able to express it — the compliance suite drives conflict, no-op, and chained-advance through both transports ("fails closed" is untestable until the fake can lie, the rule ADR-0018 set for resume).
- The `followup.ts` premise "the obvious target templates end in `git.push` + `pr.open` — a steering message would republish" inverts deliberately: the tail now exists, but gated and guarded; the module's comment moves with the code in the implementing slice.
- New i18n error code `publish_conflict` in both locales; `branch.pushed` timeline events carry the commit SHA.
- The migration is additive only; no daemon version constraint is introduced.
