# ADR-0014: Retry Re-Resolves Agent Bindings Against Current Configuration

- Status: accepted · Date: 2026-07-27

## Context

Task retry (`POST /tasks/:id/retry`) copied every configuration-derived field of the previous run verbatim — `agentBindings`, `modelResolution`, `resourceManifest`, `budget` — under the comment "pinned — retries never re-resolve". That pin was designed for transient failures (provider hiccups, worker crashes): same inputs, same plan, reproducible. But it makes retry structurally unable to heal the other major failure class, configuration failures, and the cost asymmetry is brutal: a retried run re-executes the whole pipeline from checkout (clarify loop, plan approval, full implementation — all billed) and then dies at the exact step the stale resolution doomed it to. The motivating incident: a requirement-delivery run whose reviewer slot froze `gpt-5.1-codex`, a model id the deployment's ChatGPT-account Codex auth cannot serve; the operator fixed the project's grants, and the only working recovery was re-filling the submission form — the Retry button was a trap that would have re-billed everything and failed identically.

Two facts settled the design space. First, resolution-shaped failures are not classifiable from `runs.error.code`: the incident finalized as the catch-all `model_error` (executors normalize most upstream rejections to it), and `executor_unavailable` never reaches a run's error at all (it is a submit-time code; the runtime analogue is a worker decline that leaves the run deferred) — so any "auto-re-resolve only when the failure looks configuration-shaped" scheme degenerates into message sniffing. Second, `resolveAgentBindings` is deterministic given the same project configuration: when nothing changed since submit, re-resolving reproduces the previous bindings exactly, so re-resolution strictly generalizes copying — behavior differs only when configuration changed, which is precisely when the operator wants it to.

## Decision

1. **Retry is a re-submission of the pinned task.** The template version and params snapshot stay pinned (a republished template must not change a task's plan or inputs mid-flight — the existing `params_snapshot` rationale in the domain model is untouched). Everything derived from *project configuration* is re-derived exactly as submit derives it: agent bindings and model resolution (`resolveAgentBindings`, including executor availability, capability, grant, registry-status, and credential checks), the resource manifest (`authorizeResources` — a revoked skill grant no longer rides along on a copied manifest), the budget (from the pinned compiled spec), quota headroom, and repo-ref ownership. Submit and retry share one resolution helper so the two paths cannot drift.
2. **Submit-time agent overrides persist on `tasks` and re-apply at retry.** The `agents` overrides a user picks on the submit form were consumed at resolution and stored nowhere, so a re-resolving retry could not distinguish "the user deliberately chose this executor" from "the template default resolved to it". A new `tasks.agent_overrides` column records the raw override object at submit; retry passes it back through resolution. Tasks created before the column exists retry with template defaults — a recorded consequence, not a bug.
3. **Freezing remains per-run, never per-task.** Each run still records the resolution it actually executed with — `runs.model_resolution` stays the execution and pricing record, frozen at run creation, because grants can change mid-run and usage attribution must be unambiguous. This ADR narrows the freeze's scope, not its existence: reproducibility of a run's *record* is intact; determinism of *retry-follows-previous-choice* is what changes.
4. **`assertResolutionCredentialed` is deleted, subsumed by the full gate.** ADR-0013 amendment 1 added it so a credential deleted between runs failed at the retry endpoint instead of mid-run; full re-resolution enforces the same `provider_credential_required` gate (and every stronger one) before the run row exists, so the narrow check has no remaining caller.
5. **Retry fails fast with submit's error codes, and ignores task-type disabling.** Current configuration that cannot satisfy a slot surfaces at the endpoint as the same 400s submit produces (`no_models_granted`, `model_unresolvable`, `provider_credential_required`, `executor_unavailable`, `executor_capability`, `quota_exhausted`, …) — never mid-run. `taskType.enabled` is deliberately not checked: disabling a task type blocks *new* submissions from the catalog, not the retry of a task that already exists.
6. **The UI states what retry means before it runs.** Retrying re-executes from checkout and re-asks earlier checkpoints (answered questions, approved plans); the Retry button gains a confirmation stating both that and that the run binds against today's configuration. Re-resolved bindings are visible where they always were — the run detail header chips and the Details card render each run's own resolution.

## Alternatives considered

- **Keep copying (status quo).** Preserves determinism nobody benefits from: with unchanged config, re-resolution yields the same bindings anyway; with changed config, the copy re-bills a full pipeline into a predetermined failure.
- **A second explicit action ("Retry with current configuration") beside plain Retry.** Clearest contract on paper, but two buttons where operators almost always want the second, and the first remains the trap this ADR exists to remove.
- **Auto-re-resolve only on resolution-shaped failures.** Not implementable honestly — `model_error` is a catch-all and `executor_unavailable` never lands in `runs.error.code`, so classification means sniffing free-text messages.
- **Reconstructing override intent by diffing `agentBindings` against template defaults.** Fragile: the `__default__` sentinel and demo-mode rebinding make "what the default would have been" depend on deployment env at submit time; persisting the user's actual input is exact and cheap.

## Consequences

- The incident's task becomes retryable: after fixing grants, retry binds the reviewer to a servable model and proceeds — no form re-fill, no doomed re-run.
- A retry after a config change can bind a different provider, executor, or model than run #1 — per ADR-0013's consequence, that is the intended meaning of "the project chose this"; each run's own record shows what it ran with.
- A retry can now be rejected for reasons the original submit passed (quota exhausted since, all grants revoked, executor no longer registered) — an earlier, cheaper failure than the mid-run one it replaces. `executor_unavailable` and its sibling codes join the localized error catalog for the first time on this path.
- Tasks predating `agent_overrides` retry with template defaults; a user who overrode a slot on such a task and needs the override back re-submits once, after which the override persists.
- Retry now writes inside a transaction (run insert + `tasks.latestRunId` together) and its audit row records the source run — parity with submit's atomicity and traceability.
