# ADR-0018: Follow-Up Steering — a Run Inherits a Workspace and a Session, Not a Lifecycle

- Status: accepted · Date: 2026-08-04 (revised pre-implementation after cross-ADR review: the enforcement sites of Decision 1 enumerated, Decision 3's column default corrected, Decision 4 rewritten against the reaper that shipped between drafting and review, Decision 5's "read nowhere" corrected)
- Builds on ADR-0005 (the step seam is where a follow-up attaches) and ADR-0017 (affinity and the lease are what make "the same workspace" a thing the platform can promise). **Amends ADR-0014**: retry re-resolves configuration, a follow-up deliberately does not — see Decision 2. **Defers an amendment to ADR-0012**: publication from a follow-up needs a tip-advance lease and is out of scope here, see Consequences. Charted as Phase C of [docs/plan/m2-plan.md](../plan/m2-plan.md); motivation in [docs/plan/multica-analysis.md](../plan/multica-analysis.md).

## Context

A finished run is a dead end. The agent produced a branch, a patch, and a conversation; the operator reads the result and wants to say one more thing — *"also handle the empty-list case"*, *"use the existing helper instead"*. Today the only route is a new submission: a fresh workspace, a fresh clone, a fresh conversation that knows none of it, and the whole pipeline re-billed from checkout. The work the agent already did is not lost, but everything it *knew* is.

What makes this awkward is that three identities are conflated in one row today. **Run identity** is the unit of billing, audit, SSE and the state machine. **Workspace identity** is a directory on some host, currently named after the run. **Session identity** is an executor's conversation handle, currently stored on a step of that run. Steering needs the second and third to outlive the first, and nothing in the schema lets them.

The temptation is to reopen the finished run — same row, back to `running`. That is the option this ADR spends its first decision rejecting, because terminal-is-absorbing is not a convention here but a load-bearing invariant with eight enforcement points, and because `finalizeRun` does things on the way out (stamps `finished_at`, overwrites `usageTotals` wholesale from the meter) that a reopened run would inherit as corruption rather than history.

A second fact shapes the rest: an executor's session id is only meaningful against the executor and the model that minted it, and a workspace only contains what the manifest pinned at *its* submission materialized into it. That is what makes this ADR diverge from the one immediately before it in spirit — ADR-0014 argued that re-resolving configuration strictly generalizes copying it. For a follow-up, it does not.

## Decision

**1. A follow-up is a new run, not a reopened one.** Run #N+1 under the same task, `kind = 'followup'`, `parent_run_id` pointing at its predecessor. `LEGAL_TRANSITIONS` is untouched and terminal stays absorbing. The reopening alternative was rejected on four independent grounds, any one of which is sufficient: the invariant is enforced at eight sites and would have to be relaxed at all of them; `finished_at` anchors every duration and `maxDurationMinutes` computation, so a reopened run resumes against an already-exhausted deadline; `usageTotals` is written wholesale at finalize, so the second finalize erases the first run's accounting rather than adding to it; and the timeline would carry a `run.succeeded` event mid-history, which the SPA treats as permission to close the EventSource and the notification pipeline treats as a reason to fire terminal notifications a second time.

The eight, named so the count is checkable rather than rhetorical: `LEGAL_TRANSITIONS`' four empty terminal rows in `@agrippa/core`; the `canTransitionRun` guard inside `transitionRun`; the same guard again inside `finalizeRun`; `claimRunLease`'s predicate, which admits only `queued`, `waiting_approval` and unleased `running`; the engine's `already_terminal` short-circuit ahead of the claim; the API's cancel guard; `markRunFailed`'s no-op on an already-terminal run; and the worker's routing skip, which would leave a reopened run executing with deps nobody routed. A second class does not throw at all — the server's SSE loop and the SPA's `EventSource` both end on a terminal status, the daemon reaps a pinned run's workspace once it finalizes, and a schedule's concurrency policy reads terminal as "not active" — so relaxing the eight guards would buy a run that is legal to reopen and impossible to watch.

**2. A follow-up copies configuration verbatim. This is a deliberate divergence from ADR-0014, and the reasoning that ADR gave is what justifies the divergence.** ADR-0014's argument was that re-resolution *strictly generalizes* copying: `resolveAgentBindings` is deterministic, so when nothing changed it reproduces the previous bindings exactly, and it differs only when configuration changed — which is exactly when a retry's operator wants it to. That generalization property does not hold here. A follow-up inherits a session id minted by a specific executor against a specific model, and a workspace containing exactly what the previous run's pinned manifest materialized. Re-resolving could hand the inherited Claude session to Codex, or point at a model that never saw the conversation, or authorize a skill set the workspace on disk does not contain. Re-resolution would not be a more general form of copying; it would be a different run wearing a follow-up's clothes. So `templateVersionId`, `paramsSnapshot`, `faberId`, `executorId`, `agentBindings`, `modelResolution`, `resourceManifest`, `workBranch`, `workspaceRef`, `runtimeId` and `workspaceKey` are all inherited unchanged. Quota headroom and executor liveness are still re-checked, because those are about whether the work *may* proceed, not about what it is. **The corollary an operator must understand: a follow-up cannot heal a configuration failure. Retry is the tool for that, and it is the honest answer when someone asks why a follow-up will not pick up a fixed model grant.**

**3. Workspace identity moves to its own column.** `runs.workspace_key`, set to the run's own id at submit and inherited unchanged by follow-ups, so a chain of runs shares one directory. Writer-assigned rather than defaulted, because Postgres cannot default a column to another column of the same row — the migration backfills existing rows from `id` and the submit path writes it thereafter. That the key *is* the run id for every run that is not a follow-up is worth stating, because it is what makes the version skew below survivable everywhere except the one case that matters: for an ordinary run, a directory named by key and a directory named by run are the same directory. `@agrippa/workspace` takes a pure parameter rename (`runId → workspaceKey`); the package never knew what a run was, which is why this is a rename rather than a redesign. The central `WorkspaceManager` keeps its run-keyed interface and resolves the key internally, so the engine does not change. `DispatchWorkspaceSpec` gains the key and the daemon substitutes it — that single substitution is the entire remote side of the feature.

**4. Workspace lifetime becomes a retention policy, not a finalize side effect.** Today the engine deletes the workspace when the run finalizes, and the daemon deletes it when the server says the run finished — the `reapableRunIds` piggyback on the claim long-poll, which landed days before this ADR and is keyed on precisely the fact that is about to stop meaning "this directory is dead". Both are keyed on the run, and a follow-up needs the directory to outlive its ancestor. Finalize therefore *releases* rather than deletes, stamping an expiry; collection groups by `workspace_key` and takes the latest expiry in the group, so a follow-up extends its ancestor's workspace by existing. The piggyback carries expired workspace keys instead of finished run ids — the same idempotent, unacknowledged, windowed shape, re-keyed. The server owns the policy and each host owns its own filesystem — the same split ADR-0017 made for credentials — so the daemon additionally enforces a local time-to-live that holds even when it loses server contact, which is the property that matters on a laptop; its existing boot sweep is promoted from a backstop for a daemon that was offline into the local half of the policy. Retention defaults to zero (today's behaviour) until the collector is proven.

**5. Resume becomes a detection capability, and the engine fails closed without it.** `capabilities.resume` is a boolean today that nothing branches on — every capability check in the compiler and the resolver reads `subagents`, `skills` or `mcp` and none reads this one — which is the tell: "accepts a resume argument" and "can prove the context loaded" are different properties, and only the second is worth anything.

It is not, however, untouched, and the review found the trap. The flag is mirrored in `EXECUTOR_CATALOG`, which the API and the SPA trust, and the two copies are reconciled at worker boot by a parity check whose rule is *the catalog may promise less than the executor delivers, never more* — written as a boolean implication over the flags. Three values need an ordering, or that check reads `"none"` as satisfying a catalog promising `"verified"`, since both are truthy: a silent fresh start presented as continuity, arriving through the one mechanism that exists to stop capability drift. The comparison becomes ordering-aware in the same slice as the type. It becomes three-valued — `none`, `unverified`, `verified` — and executors report per invocation whether the session actually resumed or started fresh. An executor that cannot prove it is never handed a session id at all, which structurally prevents a silent fresh start being presented as continuity. Where resumption is verified and fails, the engine re-invokes once with a context-loss disclosure composed into the step's instructions. **This slice lands before the feature that needs it, because it also hardens the crash-resume path that exists today** — which currently hands a session id to an executor that may quietly ignore it, and reports the result as though nothing happened.

**6. The disclosure is engine-composed, per invocation, and never touches the workspace.** It goes into the step's `instructions` — the volatile channel — not into `systemPrompt` (a registry row shared across runs) and not into any file in the workspace. The last of those is enforced rather than conventional: the engine resets the agent project config and re-materializes skills from their pinned versions before every attempt, so a file-borne disclosure would be erased before the invocation that needed it — and that same rewrite is what keeps the tree byte-identical for the prompt cache. A steering message is untrusted operator text on the same footing as a task parameter: it is interpolated in a single non-rescanning pass, so a message containing template syntax is delivered verbatim rather than evaluated.

**7. What executes is a synthetic two-step flow, built in memory.** Not a new template kind, and not re-entry into the compiled flow — re-entry replays answered checkpoints and reopens loops the run already closed, and the obvious target template ends in `git.push` + `pr.open`. The follow-up runs `attach` (assert the workspace is intact, failing `workspace_lost` when it is not) then `steer` (one agent step on the parent's slot and model role), inheriting the base template's agents, models, resources and workspace settings. The token limit is bounded independently, because a follow-up's meter starts at zero and the base run's limit would otherwise apply again per follow-up.

**8. Coalescing is queue-level, not in-process.** Several messages sent in a burst become one follow-up, enforced by a delayed send keyed on the workspace, because the API runs multiple replicas and an in-process debounce would be per-replica. The message is written to the run's comment timeline before anything else happens, so it is visible immediately whatever the queue does with it; a message that arrives while a follow-up is running becomes the next one rather than joining the current.

## Alternatives considered

- **Reopen the finished run.** Rejected on the four grounds in Decision 1. Worth recording that the attraction is real — one row, one timeline, no parentage to explain — and that the cost is entirely in invariants that are cheap to keep and expensive to reintroduce.
- **Re-resolve configuration like retry does (ADR-0014).** Rejected in Decision 2. This is the decision most likely to be revisited, and the honest summary is that it trades the ability to heal configuration drift for the ability to mean "continue *that* conversation".
- **A `followup` template kind, authored in YAML.** Rejected: it makes every template author responsible for a flow that has exactly one correct shape, and it puts a compile-time surface in front of a runtime concern.
- **Session ids as a first-class table.** Rejected as premature: `run_steps.executor_session_id` already persists them and the request builder already reads them, so seeding a follow-up is a query, not a schema.
- **Publication from a follow-up in the first landing.** Deferred, and not for effort reasons — see Consequences.

## Consequences

- **Publication is out of scope for the first landing, and this is an ADR-0012 problem rather than a steering one.** `applyApprovedPatch` deliberately refuses to advance a branch whose remote tip is not byte-identical to the recomputed snapshot commit — that refusal is ADR-0012's idempotency anchor, and the push behind it is a *creation* CAS: the observed tip must be absent, or already be this exact commit. A follow-up legitimately advances a tip its ancestor published, so making it push needs a tip-advance lease (an expected-tip CAS), which changes publication semantics and deserves its own amendment rather than a paragraph here. Until then a follow-up produces a patch and a diff, and publishing remains the ancestor's business.
- **A concrete bug in the same area, found while writing this.** The Codex executor keys its session home by run id, under the OS temp directory. A follow-up is a new run, so it could not see its own thread even with everything else correct, and the OS may reap the directory regardless. Session scope must follow the workspace, not the run — which the workspace-key work makes expressible.
- **Daemon version skew becomes a correctness hazard rather than a compatibility one.** A daemon that ignores the workspace key clones into a fresh directory and reports success, so the follow-up silently loses the work it was supposed to continue. Runtimes therefore advertise features, and a dispatch to a runtime that does not claim workspace-key support is refused rather than degraded.
- **The compliance suite gains resume as a dimension**, run through both transports: honored, rejected-then-disclosed, never-resumed-when-unverified, protocol violation fails closed, chained follow-ups, crash mid-follow-up, and the terminal ancestor never mutated. `FakeExecutor` must be able to express both outcomes and a protocol violation — "fails closed" is untestable until the fake can lie.
- **Central host affinity remains open.** Remote runs are pinned by ADR-0017 and inherit that pin for free. A central run has no host pin, so a follow-up can be picked up by a worker that does not have the directory. The first landing declines at claim time (bounded, and correct); a per-host queue is the real fix and follows the same route-by-capability shape Phase B established. **A dead pin fails `workspace_lost` and is never re-routed** — re-routing lands the agent in an empty directory and lets it report success.
- The SPA gains a follow-up action on finished runs and a "continues #N" affordance; cross-run timeline stitching is deliberately not attempted in the first landing.
- Steering a run that is still `running` or `waiting_approval` is a different feature with a different failure model, and is not in scope: the plan says *finished*.
