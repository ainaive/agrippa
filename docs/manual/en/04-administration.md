# Administration

Two admin surfaces exist: **org administration** (the sidebar's *Admin* section, visible only to the org admin role) governs the shared registries; **project administration** (each project's *Settings* page, visible to project admins) governs one project.

## Org roles

Two org roles exist: **org admin** and **org member**. Org admins manage the registries below, invite new members, and can read the audit log; they get *no* implicit access inside projects — project membership is always explicit.

## Accounts & onboarding

Self-registration is **closed** — onboarding is invite-only, so the instance isn't open to arbitrary sign-ups.

- **First admin** — created out-of-band via the bootstrap script, not through the UI:
  ```sh
  AGRIPPA_BOOTSTRAP_EMAIL=you@example.com \
  AGRIPPA_BOOTSTRAP_PASSWORD='choose-a-strong-password' \
  bun --env-file=../../.env.local apps/api/src/cli/bootstrap-admin.ts
  ```
  It's idempotent on email, so re-running with the same address is a no-op. The password is hashed with the same routine the login flow uses, so the account signs in at the login page immediately.
- **Inviting members** — org admins open **Admin → Members**, enter an invitee's email, and generate a one-time invite link (valid 7 days). Share the link out-of-band (Agrippa has no email sender). The invitee opens it, sets their name and password, and is created as an **org member** — then signs in normally. Pending invitations show in the list and can be revoked before they're used. Each token is stored hashed, so a database leak alone can't redeem an invite.

## Registries (Admin section)

Each registry has its own page in the Admin sidebar section, with create and edit dialogs — resources are managed entirely from the UI.

**Models** — registrations of provider models: display name, provider model id, a **tier** (`strong` / `balanced` / `fast`), context window, and a **selection rank** (lower wins when several granted models share a tier). Templates request tiers, never concrete models, so upgrading the fleet is a registry edit plus project grants — no template changes. Models can be disabled without deleting them.

**Fabri** — the preset agents (persona + system prompt + avatar), editable in place. You can add your own alongside the three builtins. Names and personas require both English and Chinese.

**Skills** — packaged instruction sets agents load (Claude Code skill format). Builtin skills ship with the platform (`git-workflow`, `test-runner`); each skill has immutable semver versions (added via *New version*) and templates reference them as `slug@range` (e.g. `builtin/git-workflow@^1`). Versions carry a status: if no active version satisfies a template's range anymore, submissions and retries that require the skill are rejected (`skill_version_unavailable`) instead of failing mid-run.

**MCP servers** — Model Context Protocol integrations (e.g. GitHub). Register the transport (`stdio`/`http`/`sse`) and JSON config; the optional **auth token is write-only** — it's encrypted immediately and the UI only ever shows "auth configured". Leave the token field empty when editing to keep the stored token, or use the explicit remove switch to clear it. Config edits bump a revision number recorded by runs for auditability. A disabled server counts as unregistered at submit and retry time: templates that require it are rejected up front, optional references are simply left out of the run.

**Workers** — the worker fleet's live state: one row per worker container with its liveness (**Live**, or **Stale** after 2.5 missed heartbeats), the executors it registered (with the provider logins its environment can authenticate), and its build version. Runs are routed to a worker that has *every* executor the run's agent slots need, so this page is where to look when a submission is rejected with "executor unavailable" — it shows exactly which workers advertise what. The list refreshes every 10 seconds. The **Remote runtimes** section below it manages daemon tokens for bring-your-own-compute machines: issue a token (shown exactly once — store it immediately), watch each runtime's online state and executor advertisement, and revoke a token to cut a machine off instantly.

**Templates** — every orchestration template with its version history. Clicking one opens the **editor**: edit the YAML source, **Validate** (a dry-run compile listing every issue at once, plus a live preview of the submission form the inputs will generate), **Save draft**, then **Publish**. Published versions are immutable — the publish button moves the "latest" pointer that new submissions use, while running and historical runs keep their pinned versions. Builtin templates re-publish automatically when the platform ships changed sources.

## Project settings (Settings page, project admins)

- **General** — rename the project, edit its description, and (in the danger zone, behind a confirmation) **archive** it: the project disappears from switchers, and submissions and retries are refused (`project_archived`) — including from API keys and schedules — while historical runs and data stay readable.
- **Members** — add by email (the person must have an account), change roles, remove (with confirmation). A project always keeps at least one admin; the platform blocks demoting or removing the last one.
- **Resources** — the grant toggles per registry type. This is the gate: a template requirement that isn't granted here makes submission fail fast with a named error. **Optional** resources are also gated — an optional skill or MCP server (for example the GitHub server behind an "open a PR" step) is withheld from the run unless it's granted, never resolved with a shared credential. A step that explicitly requires that resource is then skipped; a step that merely could use it runs without it.
- **Repositories** — git remotes the project's runs may check out: provider, URL, default branch, optional access token (write-only, encrypted; injected per git call and scrubbed before agent code runs — it authenticates clone, push, and PR creation). The provider decides whether a publish can complete: GitHub, GitLab, and GitCode create the pull request; generic Git pushes the branch but the run must open the PR manually.
- **Providers** — per-project model-provider API keys. Pick a provider (e.g. **Aliyun Bailian (DashScope)** for Qwen models), paste its API key (write-only, encrypted — the UI only ever shows "key configured"), and optionally override the endpoint for regional deployments (Bailian international workspaces use a workspace-scoped `*.maas.aliyuncs.com` host). Overrides must resolve only to public, global-unicast addresses; internal, private, and special-use destinations are refused. A project credential **overrides** the platform workers' own keys for that provider; removing it falls back to them. Some providers (Bailian) have no platform fallback — submitting a task that resolves to their models without a credential fails with a named error pointing here. Replace the key in place to rotate; running steps pick the new key up at their next step. Changing the endpoint later requires re-entering the key in the same action — endpoint and key travel together, so a stored key can never be redirected to a new host.
- **Notifications** — outbound endpoints that fire when a run needs approval, a checkpoint expires, or a run finishes (succeeded / failed / cancelled / timed out). Three kinds: a **Feishu** custom-bot card, a **DingTalk** robot card, or a **generic webhook** (JSON POST signed with `X-Agrippa-Signature: v1=<hex HMAC-SHA256 of "<timestamp>.<body>">`; receivers must answer 2xx within 10 seconds). The signing secret is write-only; it's required for generic endpoints and optional for the IM bots (paste the bot's signing key to enable signature verification). Each endpoint carries its own language for the card copy and an optional event filter (no selection = every event). Cards deep-link to the run, which is why the deployment's `AGRIPPA_BASE_URL` must be the address your team actually opens. **Send test** posts a test card immediately; the **Recent deliveries** panel shows every delivery with its status, attempt count, and receiver response, and failed deliveries can be retried from there. Changing a signed endpoint's URL requires re-entering its secret — URL and secret travel together, so a stored secret can never be redirected to a new host.
- **Schedules** — submit a task on a recurring cron schedule (five fields, in an IANA timezone the platform applies for you, DST included). Pick the task type, a cron expression, and what should happen when the previous run has not finished: **skip** (default — one late weekly report beats two overlapping ones), **queue**, or **replace** (cancel the previous run first). `pm.weekly-report` is the obvious first one.

  Stored parameters are frozen, which matters for anything date-shaped: a weekly report whose reporting period never moves is useless. Put a **date token** in a text parameter and it is replaced when the schedule fires, in the schedule's timezone — `{{today}}`, `{{yesterday}}`, `{{thisWeekStart}}`, `{{thisWeekEnd}}`, `{{lastWeekStart}}`, `{{lastWeekEnd}}`, `{{thisMonthStart}}`, `{{lastMonthStart}}`, `{{lastMonthEnd}}` (all `YYYY-MM-DD`, weeks starting Monday). A reporting period of `{{lastWeekStart}}..{{lastWeekEnd}}` gives last week, every week. That is the whole list — it is deliberately not a formula language.

  Schedules are created **from a task**, not from this page: open the catalog, fill in the task's form as if you were submitting it, then choose **Run on a schedule**. That way a schedule carries exactly the parameters a real submission would, and the platform rejects one whose parameters could never produce a run — at creation, rather than the following Monday. This page manages what exists: pause, resume, delete, and see why one stopped.

  A schedule **runs as the person who created it**, and that authority is re-checked at every firing rather than frozen at creation: it can do exactly what its owner could do right now, and never more. When something makes that impossible for good — the owner loses access to this project, the project is archived, the task type is withdrawn — the schedule is **disabled and announced**, through the notification endpoints and the audit log, rather than quietly skipped. That is deliberate: a schedule that silently stops is indistinguishable from one that was never created, and you would find out weeks later. Fixable problems (an exhausted quota, a missing resource grant, no worker for the required executor) behave differently — the schedule stays on, the error is shown on its row and sent as `schedule.failed`, and the next firing tries again. Re-enabling a disabled schedule clears its reason; whether the underlying problem is actually fixed is re-checked when it next fires.
- **Webhook triggers** — a URL an external system POSTs to in order to start a task: CI finishing, a deploy landing, a form submission. Created from a task like a schedule (catalog → fill the form → **Trigger by webhook**), managed here.

  Two things are worth knowing before you wire one up. The URL is a **capability** — anyone holding it can reach your trigger — so a **signing secret is required**, and every request must carry `x-agrippa-timestamp` and `x-agrippa-signature: v1=<HMAC-SHA256 of "timestamp.body">` computed with it. Requests more than five minutes old are refused, so a captured request stops working. The dialog shows a ready-to-paste `curl` example when the trigger is created; the URL is displayed exactly once. And the platform answers **202 the moment it records the request**, before the run exists — so the sender learns that its request was accepted, never whether the run succeeded. That is why a trigger that stops working notifies you (`trigger.disabled`, `trigger.failed`) rather than relying on the sender to complain: the sender was already told everything was fine.

  Like a schedule, a trigger runs as the person who created it, is re-checked on every firing, and stops with a reason if that person loses access to the project. **Recent deliveries** shows every request received with its payload, so you can see exactly what a sender sent; failed deliveries can be retried from there. If a sender supplies `x-agrippa-delivery-id`, a retried request is deduplicated instead of starting a second run.
- **API keys** — programmatic access to this project: `Authorization: Bearer agr_<key>`. Create a key with a name and its scopes — `tasks:write` (submit, retry, cancel), `runs:read` (tasks, runs, steps, checkpoints, comments, artifacts), `resources:read` (the task catalog) — and copy the plaintext **immediately**: it is shown exactly once and only a hash is stored, so a lost key is replaced rather than recovered. Revoke takes effect on the next request.

  Two limits are worth knowing before you script against it. A key **acts as the person who created it** and is **bound to the project it was created in**: it can never reach another project, and it stops working the moment its creator loses membership here — which is also how you disable someone's automation when they leave. And a key can only reach the automation endpoints, never administration: registries, template publishing, members, quota, settings, notification endpoints, checkpoint decisions, and API-key management itself all answer `403` for a key, whatever its scopes and whatever its owner's role. Approving a checkpoint stays a human action in the browser. Every mutation a key makes is audited, naming both the key and its owner.
- **Quota** — a monthly token ceiling with a **hard stop** switch. Hard-stop quotas reject new submissions once exhausted and abort in-flight runs at the next step boundary; soft quotas are informational.

## Usage & audit

Each project's **Usage** page (sidebar) shows current-month token consumption against the quota, the remaining headroom, a daily-token chart, and breakdowns by model and by task type; the dashboard carries the headline numbers. The same data is available at `GET /api/v1/projects/:id/usage`.

Every mutation in the system — member changes, grants, template publishes, submissions, approvals, cancellations — writes an audit entry (actor, action, resource, payload, IP). Org admins browse them on the **Audit log** page in the Admin section: filter by project or action, and expand any row to see its payload. The same data is available at `GET /api/v1/audit-logs?projectId=&action=&limit=`.
