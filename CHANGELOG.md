## [Unreleased]

### Added

- **A finished run now has a Continue button.** On a run whose workspace is still held, the timeline's composer gains a second destination: the same text either becomes a comment or asks the agent to carry on, and the reader lands on the run that will do the work. A follow-up's header carries a "continues #N" chip back to its parent. The button disappears once the workspace is past retention, so the affordance and the capability expire together rather than the UI offering something the API would refuse.

- **`POST /runs/:id/followup` — steer a finished run with one more message.** The message lands on the run's thread first, so it is visible whatever the queue does with the rest; a follow-up that exists but has not started then **absorbs** it, which is how a burst of thoughts becomes one run. The run row is the coalescing buffer deliberately: the API runs multiple replicas, so an in-process debounce would coalesce per replica and produce one run each. A message arriving after the follow-up starts becomes the next one. Refused with a 409 when the run is still going, or when its workspace is already collectable — the latter because the alternative is a charged run that discovers an empty directory on a worker and fails `workspace_lost` to say what the server already knew.

- **A finished run can be continued instead of resubmitted** (the engine half). On a multi-worker fleet a central follow-up now **declines** on a host that does not hold its workspace — no status change, no retry burned — so the sweeper can hand it to a host that does; bounded at five minutes, after which a directory nobody holds honestly fails `workspace_lost` instead of circulating. A follow-up is a new run — terminal stays absorbing — that inherits its predecessor's workspace, session, template version, params, bindings, model resolution, manifest and work branch **verbatim**. Deliberately unlike retry, which re-resolves: the inherited session was minted by one executor against one model, and the workspace holds what *that* run's manifest materialized, so re-resolving could hand a Claude session to Codex or authorize skills the directory does not contain. The corollary matters and is now documented: a follow-up cannot heal a configuration failure — retry is the tool for that.

  What executes is synthesized in memory rather than re-entered: re-entry would replay answered checkpoints, reopen closed loops, and in the obvious templates reach `git.push` again. The synthetic flow keeps the base template's agents, models, resources and workspace and runs a single step bound to the slot and model role the parent's last agent step used, seeded with that step's session. Attaching is asserted before anything runs — a follow-up whose workspace is gone fails `workspace_lost` rather than letting an agent work in an empty directory and report success. The operator's message is appended after interpolation, so a message containing template syntax is delivered rather than evaluated.

  Two things the design did not foresee, found while building it. Workspace retention and steering are the same knob: at the proposed default of zero the ancestor's workspace is collected on the next sweeper tick, so every follow-up would fail — the default is now one hour, the steering window. And the compliance suite's fake workspace manager was still run-keyed, which meant it could not prove a follow-up shares its ancestor's directory; it now resolves workspace keys exactly as the real managers do.

- **Runtimes advertise what their build can do, not just which executors it has.** Daemon version skew has been a compatibility question — an older build serves less — right up to the workspace key, which makes an old build silently *wrong*: it clones into a fresh directory, reports success, and a follow-up loses the work it existed to continue, with nothing in the timeline saying so. Daemons now register a bounded `features` list, and a follow-up pinned to a runtime that does not claim `workspace-key` is refused rather than degraded. Refused as a **deferral**, not a failure: the run waits with a `run.deferred` event naming the reason, burns no retries, and proceeds by itself once that machine is upgraded — which failing it would not. Admin → Workers flags the runtime so the operator knows which machine to rebuild. Unknown feature strings are stored rather than rejected, so a newer daemon claiming something a lagging server has never heard of stays forward compatible.

### Changed

- **A workspace outlives the run that made it.** Deleting one was a side effect of finalizing a run, which only works while a directory belongs to exactly one run — and a follow-up continues its ancestor's. Finalizing now *releases* instead: the expiry is stamped inside the same compare-and-swap that writes the terminal status, so every path that finalizes releases — the engine, a cancel of a queued or paused run, a retry-exhausted failure — and none of them can leave a workspace nothing will collect. Collection groups by workspace key and requires that **every** run sharing it has released and the group's latest expiry has passed, so a follow-up extends its ancestor's workspace merely by existing, and nobody has to reason about who else holds the directory. Retention defaults to one hour — the window in which a finished run can still be steered, since a follow-up attaches to that directory; `AGRIPPA_WORKSPACE_RETENTION_MINUTES` raises it to inspect finished trees, and `0` restores immediate collection. The server owns the policy and each host owns its filesystem: central workers collect through a sweeper stage, and the daemon both takes the server's list and enforces its own age-based TTL at boot and every six hours, which is the part that still holds on a laptop that has not reached the server in weeks.

- **A workspace is no longer named after a run.** Three identities were conflated in one row: run identity (billing, audit, SSE, the state machine), workspace identity (a directory on some host), and session identity (an executor's conversation handle). Steering a finished run needs the second and third to outlive the first, so `runs.workspace_key` becomes its own column — the run's own id for everything that exists today, and inherited unchanged by a follow-up so a chain of runs shares one directory (ADR-0018 Decision 3). `@agrippa/workspace` took a pure parameter rename; it never knew what a run was, which is what made this a rename rather than a redesign. The engine and the SCM service still speak in run ids, with the translation at the workspace-manager boundary. The daemon's claim response now names spent **workspaces** rather than finished runs — the directory is what gets deleted, and a run is no longer the only thing that can name one.

  This also fixes a bug the design work surfaced: the Codex executor kept its resume threads in a `CODEX_HOME` keyed by run id, so a follow-up would have looked for its own thread in an empty directory, started fresh, and reported success. Session scope now follows the workspace.

- **An executor that cannot prove a session resumed is no longer handed one.** `capabilities.resume` was a boolean that nothing branched on, and the engine gave a crashed attempt's session id to whoever was bound — including an executor free to ignore it and start fresh, whose output was then recorded as though the conversation had continued. It is now three-valued (`none` / `unverified` / `verified`, ADR-0018 Decision 5): only `verified` receives a session id, and having received one it must report `honored` or `rejected` on `step.started`. Both shipped executors verify by comparison — the Claude SDK's init message and Codex's `thread.started` each name the session actually opened, so the claim is a comparison rather than a hope, and a false `rejected` costs one honest restart while a false `honored` would let a fresh agent speak as though it remembered. A rejection buys exactly one re-invocation on the same attempt (losing a conversation is not the step failing, so no retry budget is spent) with the dead session id withheld and a context-loss disclosure composed into the step's instructions — the volatile channel, never the shared system prompt and never a workspace file, which is reset before every attempt anyway. Silence from a `verified` executor fails the step `contract_violation`: proceeding would be exactly the silent fresh-start-as-continuity the capability exists to prevent. This hardens the crash-resume path that exists today, ahead of the follow-up steering that will depend on it.

  The three values are **ordered**, and that turned out to be load-bearing in a place the design did not expect: the worker's boot-time parity check — the one mechanism guarding against an executor drifting below what the catalog promises the API and SPA — compared flags as a boolean implication, which reads `"none"` as satisfying a promise of `"verified"` because both are truthy. It now compares `resume` by rank, through a pure `catalogCapabilityShortfall` in `@agrippa/core` with the trap pinned by its own test.

### Fixed

- **A daemon host no longer fills up with dead workspaces.** Nothing ever deleted them: every remote run left a shallow clone under the daemon's workspace root permanently, and on a machine dogfooding daily that is a slow, silent disk leak. The daemon could not fix this alone — affinity gives it a run's workspace for the run's whole life (ADR-0017 Decision 3), so the directory carries state across steps, and reaping a run that is merely paused at a checkpoint would not cost a re-clone but silently drop the completed steps' work: the next dispatch re-clones at the pinned base and continues as though that work never happened. Only the server knows a run finalized, because the engine runs centrally even when the executor does not. The claim long-poll now piggybacks `reapableRunIds` alongside the aborts it already carried, and the daemon deletes those workspaces and their platform sidecars. Bounded by a 24-hour window rather than an acknowledgement, since removal is idempotent, with a boot sweep of anything untouched for 30 days as the backstop for a daemon that was offline when its runs ended — or upgraded from a build that never reaped at all. Older daemons ignore the new field and older servers omit it; the sweep collects either way.

- **Every unattended firing now carries an idempotency key** (review round 3). Five defects, two of them consequences of round 2 — the third consecutive round where the previous fix produced the next finding, by the same mechanism each time.

  Round 2 offered two ways to stop a firing charging twice — a unique firing key, or committing the submission with its bookkeeping — and only the second was implemented. They close different windows. The transaction covers the gap between the run insert and the bookkeeping write; it says nothing about pg-boss re-delivering a job whose transaction already committed, which after a worker dies mid-ack arrives ~15 minutes later on the queue's defaults. `queue` then submitted unconditionally, `replace` cancelled the run that same firing had just created before submitting another, and `skip` only held while the previous run was still running — which by then it usually is not. Runs now carry `origin_key`, nullable with a partial unique index, written inside the submission transaction: `schedule:<pg-boss job id>` (stable across a retry, fresh per cron tick — the worker had the id in hand and discarded it), `trigger:<delivery id>`, and NULL for anything a human submitted. `submitTaskIn` raises `DuplicateFiringError`, which callers report as a skip, because `fireSchedule` routes anything else it catches into a `schedule.failed` notification — paging a project because the system refused to charge it twice is its own kind of broken. Triggers already had this property through their delivery row's `succeeded` flip; schedules had no per-firing record at all.

  Calendar reconciliation, added in round 2, read the schedule rows *before* the live calendar. Every writer commits its row first and touches the calendar after, so that ordering raced the wrong way round: a schedule created in the window was absent from the rows snapshot but present in the calendar, and was torn out as an orphan seconds after being created — enabled, no error, healthy in the UI, never firing. An edit was worse: the reconciler compared the new calendar entry against the old row and re-registered the **old** cron, and nothing downstream re-validates it, so the schedule genuinely fired at a time the UI said it did not. The calendar is now read first, which makes the rows snapshot the fresher of the two and every interleaving benign, and each unregister re-validates against the row immediately before tearing an entry out.

  The same function swallowed per-schedule failures into a bare `catch {}` — no log, no counter, no rethrow — and the counters incremented after the await, so a failure did not even show as a shortfall. If the only drift was the schedule that kept failing, the sweeper logged nothing at all, every tick, while the boot pass printed `+0/-0`: the exact line a converged fleet prints. Both were present before the round-2 refactor moved the loop into a package that takes no logger. Failures are now returned, logged with the schedule id, counted against a restored `X/N` denominator, and written to the same amber `last_error` an admin already reads on the row.

  The webhook acknowledgement still awaited its enqueue. `enqueueAfterCommit` bounds failure but never latency, and pg-boss builds its own pool that waits indefinitely for a connection — so a stalled database held the response open until Bun's 60s `idleTimeout` killed the socket, and the sender saw a connection reset rather than a status code. That is the most retry-triggering answer there is, and an unkeyed retry inserts a second delivery and a second run while the sweeper revives the first. It is no longer awaited; the durable row and `sweepTriggerDeliveries` are the guarantee.

  Finally, delivery ids were truncated to 200 characters. The reachable half was not the prefix collision but the empty string: `Headers.get` returns `""` for a present-but-empty header, `""` is not null, and the dedupe index is partial on `IS NOT NULL` — so every request carrying a blank `x-agrippa-delivery-id` collapsed onto one delivery row forever, and once that row succeeded the endpoint accepted webhooks and ran nothing, answering `200 accepted` every time. Blank is now absent, and an over-long id is a `400`: rewriting a sender's idempotency key into a shorter one turns two distinct events into a duplicate.

  A self-review before merge found four more, three of them introduced by the fixes above. Resolving the firing key inside the submission was too late for `replace`: it reached its cancellation first, killed the run its own firing had created, then found the duplicate and returned without putting anything back — an occurrence that destroyed a live run and produced nothing, worse than the double charge the key exists to prevent. The key is now resolved before the concurrency policy, ahead of anything observable. The `lastError` added to make repairs loud had no clearing path, so one transient blip marked a schedule broken in the UI forever — a *disabled* one could never clear it at all — and it reported unregister failures as registration failures, wrote to rows that do not exist, and re-stamped an unchanged message every minute on every replica. And a genuine constraint violation, which two concurrent invocations of one firing can still reach, fell past `DuplicateFiringError` into the failure path: on schedules it paged the project with the raw constraint name; on triggers it flipped a delivery to `failed` behind a run that had succeeded — unclearable, because Retry refuses a delivery that already has a run id.

  The awaited enqueue, meanwhile, had been fixed at the two inbound sites and left on the front door. `submitTask` backs `POST /projects/:id/tasks`, the first entry on the API-key allow-list, and it is the one API-key-reachable mutation with **no** idempotency guard at all: same stall, same connection reset, same retry, but a second task, a second run and a second charge with nothing to dedupe against. It is no longer awaited.

- **A firing that keeps failing is recorded rather than vanishing.** Making unexpected errors propagate so the queue retries them was right while retries remain — but pg-boss neither emits on handler failure nor dead-letters here, so the *last* throw was perfectly silent: the job rested in `failed`, the row kept a null `lastError`, no notification went out, and the UI showed the schedule healthy. That is worse than the wrong attribution it replaced. Both firings now take the last attempt as a signal to record instead, the same shape the notification handler beside them already used — which also catches the permanent-but-untyped cases (a template row that cannot be upgraded, params that fail a bare property read) that are the project's problem despite not being an `AppError`. The worker's success line carries the run id again, so a firing can be correlated to its run from the log.

- **Disabled-reason copy reads as a sentence.** The reason was resolved through the settings catalog, whose strings are written to stand alone as a status line — so the card said *"was disabled and will not run again: Stopped: its owner no longer has access to this project.."*, with a doubled clause and a doubled terminator, in all four schedule/trigger renderings and both locales. The notifications namespace now carries its own clause-shaped wording.

- **A notification delivery can no longer be failed out from under a successful attempt.** The endpoint-disabled write had no `status = 'pending'` guard and ran before the claim, so a duplicate job could stamp `failed` over a delivery another attempt had already succeeded — and a succeeded row holds the request snapshot in `payload`, which the retry would then have re-rendered from instead of the event.

- **Schedule and trigger notifications now say what happened.** Every one of them shipped with an empty body. `deliverNotification` sourced its template variables from `run_events`, but a project-scoped event — a schedule or trigger that stopped — has no run to hang an event row on, so its payload sits on the delivery row instead, which nothing ever read. The card an operator received said: *The schedule "" in Acme produced no run this time: .* That is the only channel reaching a human when unattended work breaks, and it reached them with nothing in it. Two bugs in one path: the payload never arrived, and `error` is emitted as a formatted string while the renderer cast it to `{code, message}`, so a truthy string took the object branch and rendered empty even when the payload was there. Disabled reasons also interpolated as raw enums (`owner_lost_access`) into prose; they now resolve through the same catalog the settings page uses.

- **An unattended firing no longer spends its occurrence on an infrastructure fault.** `fireSchedule` and `fireTrigger` classified only a duplicate firing and funnelled everything else — deadlocks, statement timeouts, plain bugs — into the "record and announce" path, which *returns* rather than throws. The pg-boss job then completed successfully, so a weekly schedule lost a week to a transient error, and told the project it was at fault. Only `AppError` and `SubmitError` are now treated as the project's problem; anything else escapes so pg-boss retries, which is what the engine does with unexpected errors and what the worker's own comment at the call site already claimed. The worker also logs the outcome's `error`/`reason` rather than just its discriminant — previously a lost firing printed `"failed"` with no cause.

- **Two remaining reconciler races** (review round 5, found by codex and CodeRabbit independently — they reported the first one with the same fix). The healing clear tested ownership in JavaScript against the rows snapshot but filtered the UPDATE by id alone, so a genuine firing error committed in between was wiped and the schedule rendered healthy until its next failure; ownership is now a SQL predicate evaluated under the row lock. And the register leg wrote `cron`/`timezone` straight from that same snapshot while the two unregister legs re-validated first — but the snapshot is taken once and the loop is serial with a round trip per repair, so a row late in the list acted on a reading many seconds old, and an edit landing in that gap had its old cron restored under it. Every repair now re-reads the row immediately before writing. Neither mistake is durably worse than the other and both self-heal within a tick, so the docstring's justification for guarding only one leg was wrong and has been rewritten. The 60s sweeper also gained a re-entrancy guard: `setInterval` does not await its callback, so a slow sweep could overlap itself and run two reconciles that invalidate each other's snapshots.

- **`Bearer` is matched case-insensitively**, per RFC 9110 — `bearer agr_…` previously fell through to the session branch and answered a bare `unauthorized`. The daemon router's duplicate copy of the same parse now calls the shared helper that describes itself as the one implementation.

- **A notification delivery is no longer failed while its POST is in flight.** `sweepNotificationDeliveries` gets the two guards `sweepTriggerDeliveries` — the copy made from it — was given in review round 1: staleness measured by attempt age rather than row age, and a recency guard on the exhaustion update. Without them a delivery mid-request could be stamped `failed`; the success path overwrote it back, but in that window the admin UI offered Retry, and a click re-sent a duplicate webhook to the customer's endpoint. A delivery in its backoff sequence was also re-enqueued on every tick.

- **Unattended submission is now atomic with its own bookkeeping** (review round 2). Seven more defects, three of them consequences of round 1 — each time because the fix went to the site the review named rather than to the class of sites that shared the defect.

  `submitTask` committed the run, then the caller recorded that it had happened. A crash in that gap left the delivery `pending` or the schedule's `lastRunId` stale, and the retry — whose claim window is deliberately *shorter* than the retry delay, so that legitimate retries get through — submitted a second charged run. `submitTaskIn` now takes the caller's transaction, so the run and the record of it commit as one unit; the enqueue stays outside as best-effort. The read chain it depends on (`assertQuotaHeadroom`, `verifyRepoRefs`, `resolveRunPlan` and their callees) widened to `DbOrTx`, which is what the rest of the codebase's tx-aware helpers already took. Schedules were the worse case: their queue retries immediately with no claim at all, and a lost `lastRunId` is precisely what the `skip`/`replace` concurrency check reads — so it stopped skipping and started "replacing" a run that had already finished.

  Two more found while verifying, which the report did not name. The `try` spanned the bookkeeping as well as the submission, so a failure *after* the run committed marked the delivery `failed` and fired `trigger.failed` for a run that was alive and billing; the `try` now covers only the submission. And Retry gated on status alone, so clicking it on such a delivery minted yet another run — it now refuses any delivery that already has a `run_id`.

  The rest: both inbound `enqueueTriggerDelivery` calls were still bare, so a queue outage 500'd an accepted delivery and the sender's retry — lacking the *optional* delivery-id header — inserted a second one; the `trigger.failed` path wrote its terminal status separately from its announcement, exactly the shape fixed for the disable path one branch above, and `failed` is what makes the retry's claim reject, so the notification was lost for good; Retry left `attempts` and `lastAttemptAt` untouched, so an exhausted delivery was re-failed by the sweeper the moment it aged and a click within 20s silently no-opped, both hazards the notification retry's own comment names; and the HMAC was computed over decoded text, so a body containing invalid UTF-8 could never verify and was reported as a wrong secret — it now hashes the wire bytes and decodes afterwards.

  Schedule registration got live recovery it was missing. Round 1 made it best-effort so a queue hiccup would stop 500-ing a schedule that existed — but reconciliation ran only at boot, which turned a loud wrong answer into a silent one: the schedule never fired until a restart, and an edited one kept its old cron while the UI displayed the new. A `schedule-calendar` sweeper stage now diffs the rows against `boss.getSchedules` every tick, writing nothing when converged and removing entries whose row is gone. `enqueueAfterCommit`'s docstring was corrected too — it asserted that *every* post-commit send in the codebase has a sweeper behind it, and schedule registration was the one where that was false while its warning told operators otherwise.

  Finally, the nine new management mutations now write their audit row inside the mutation's transaction, per ADR-0014 decision 3. Verified and scoped deliberately: **all 50 route call sites** in the codebase are non-transactional, so this is a long-standing pattern rather than a Track T regression — the other 41 are recorded as their own change rather than enlarging a PR under review. The API-key case was the one worth not deferring: a failed audit after the key row committed left a live credential whose only plaintext died with the request and whose creation the audit log had no record of.

- **Unattended submission is now loss-proof and duplicate-proof** (review round 1 on Track T). Six defects, every one a case where the code contradicted a rule the repo had already written down.

  `submitTask` commits the task and run and then enqueues — and its own comment says the worker's straggler sweep makes that loss-proof. But the schedule and trigger handlers treated an enqueue throw as a *submission* failure, so a transient queue error produced a run the sweeper duly executed **and** a second one on retry, while the delivery log said "failed" with no run id. Post-commit sends are now best-effort at all five call sites, each of which already had a sweeper behind it. The sweeper itself was a single `try` block, so one straggler with an underivable executor set aborted lease expiry, offline-runtime detection, checkpoint recovery and the delivery sweeps — every tick, indefinitely; each stage is now isolated.

  `trigger.fire` was created with pg-boss's default `standard` policy while its sends passed `singletonKey`, which on `standard` enforces nothing — as the comment ten lines above it, an existing test, and `design/04` all say. It is now `exclusive`, and `fireTrigger` claims a delivery by CAS before submitting rather than reading its status, so a redelivered job racing a sweeper re-enqueue can no longer both submit. Accepted deliveries had no sweeper at all (the index one would need was already there, unused), and a stranded `pending` row was unreachable, because Retry only moves `failed → pending`. Added `sweepTriggerDeliveries`; a duplicate delivery-id whose original never got a job now re-enqueues instead of silently answering 200.

  Disabling a schedule or trigger flipped `enabled` first and announced afterwards — and that flag is exactly what makes the retry skip, so a failure in between lost the audit row, the notification and the cron cleanup permanently, the run-less notification being unreconstructible by any sweeper. Flag, audit row and delivery rows now commit in one transaction; boot reconciliation also unregisters disabled schedules, which it never did, so a stale cron entry no longer wakes a worker forever. The CRUD handlers' queue calls are try/caught, making true a comment that already claimed they were best-effort — a queue hiccup previously returned 500 for a schedule that had in fact been created and would start firing at the next boot.

  The inbound trigger's size cap was a `Content-Length` check, which `Number("abc")` walks straight past (`NaN > limit` is `false`) and which chunked encoding omits entirely — so the real ceiling was the runtime's 128 MiB, roughly 2048× the documented 64 KiB. The body is now bounded while being read, rejecting rather than truncating, since truncation would change the bytes the signature covers. And deleting a trigger left its AES-GCM signing secret orphaned in `secrets` with no reverse cascade and nothing able to find it again; it is now deleted in the same transaction, matching what notification endpoints and provider credentials have always done.

- **Archiving a project now actually stops new work.** `project.archive` has always written `projects.status = 'archived'`, and nothing anywhere read it — the only two references to the value in `apps/api` and `packages/orchestration` were the write itself. Both manuals nevertheless promised that archiving "stops accepting submissions"; in practice the project merely dropped out of the switcher's active list, and a submit or retry against it still succeeded. That was survivable while a human had to click Submit. It stops being survivable now that work can arrive unattended — an archived project is precisely the one nobody is watching, so runs would accumulate and burn quota unseen. Submit and retry now both answer `409 project_archived`; reading history is untouched, since archiving preserves rather than hides.

### Added

- **Inbound webhook triggers** — a signed URL an external system POSTs to in order to start a task, completing M2 Track T. Track N's outbound pipeline inverted: a token plus a signing secret, a durable delivery log with payload inspection, and replay — the HMAC is verified here rather than generated, using deliberately the same `x-agrippa-timestamp` / `x-agrippa-signature: v1=…` convention the platform sends, so there is one dialect in both directions rather than two to remember.

  Three decisions are worth recording. The token travels **in the URL path**, not a header, because the senders that matter (CI runners, IM bots, hosted git providers) can all POST to a URL and many cannot set `Authorization` — which makes the URL a capability, and is exactly why **the signing secret is mandatory** here although it is optional on outbound IM endpoints: an unsigned inbound trigger is an open "spend this project's tokens" endpoint for anyone who ever sees the URL in a proxy log or a CI transcript. The signature covers the **raw request bytes**, never a re-serialization, and timestamps outside ±5 minutes are refused in both directions so a fast sender clock cannot buy a longer replay window. And the request **records and acknowledges while the worker submits**: the delivery row is written before the `202`, so a submission that fails later stays visible and replayable instead of vanishing with the sender's connection, and a slow submit can never become a timeout the sender retries into a duplicate run. An optional `x-agrippa-delivery-id` makes that idempotent outright via a partial unique index, and `fireTrigger` refuses a delivery that already succeeded — so at-least-once job delivery and an operator hitting replay both converge on one run.

  The consequence that shapes the rest: because the sender is acknowledged before the run exists, it can never learn that the run did not happen. `trigger.disabled` and `trigger.failed` notifications are therefore not a nicety but the only channel that reaches a human, which is the same argument that made schedules disable loudly rather than skip. The two features now share `checkWorkAuthority` for the three permanent conditions (owner lost access, project archived, task type withdrawn), since both needed exactly that check at exactly the same moment.

  The received payload is stored for inspection and **never interpolated into a prompt**: a valid signature proves who sent the bytes, not that the bytes are safe. Mapping payload fields into task parameters is deliberately left out — it is a prompt-injection surface that deserves its own design rather than a footnote here.

- **Scheduled task submission (Settings → Schedules)** — a task type, its parameters, and a five-field cron in an IANA timezone; pg-boss owns the calendar (and with it the DST edges), the worker re-registers every enabled schedule at boot so a crash between "row written" and "calendar registered" cannot leave a schedule that silently never fires. A concurrency policy decides what a firing does when the previous run is unfinished: `skip` (default — one late weekly report beats two overlapping ones), `queue`, or `replace`, which cancels cooperatively through the same path the API's cancel button uses rather than hard-finalizing a run mid-step.

  The design turns on one distinction: **conditions that will never heal on their own disable the schedule and announce it; everything else leaves it enabled and records the error.** An owner who left the project, an archived project, and a withdrawn task type are permanent, so the schedule stops, says why on its row, writes an audit entry, and emits a `schedule.disabled` notification. An exhausted quota, a revoked grant, or no worker for the required executor are fixable, so the schedule stays on, surfaces `last_error`, emits `schedule.failed`, and tries again next time. The tempting alternative — skip the firing and retry silently — was rejected deliberately: a schedule that stops quietly is indistinguishable from one that was never created, and that is the worst failure mode available to the one feature whose entire job is to run while nobody is watching. Both events are filterable per endpoint and render as Feishu/DingTalk cards in both locales.

  Schedules are created **from a task** — fill in the normal submit form, then choose "Run on a schedule" — so a schedule carries exactly the parameters a real submission would. Settings → Schedules is the management view (pause, resume, delete, and why one stopped). Two things make a scheduled run actually useful rather than nominally working. Parameters are validated **at creation** against the compiled template, so a schedule that could never produce a run is a `400` instead of a `schedule.failed` a week later — "loud but late" is barely better than silent when the point is unattended operation. And because stored parameters are frozen, a closed set of **fire-time date tokens** (`{{today}}`, `{{lastWeekStart}}`, `{{lastMonthEnd}}`, nine in all) is substituted when the schedule fires, in its own timezone: `pm.weekly-report` takes a required free-text `dateRange` that reaches both the prompt and the artifact title, so without this a weekly schedule would report on the same fixed week forever. The token set is deliberately closed — no arithmetic, no formats, no nesting — because the failure mode is growing a second expression language beside the deliberately non-Turing-complete one in ADR-0006.

  Authority is checked **at fire time** rather than revoked eagerly, using the same `member` gate the manual submit path applies — so a schedule can do exactly what its owner could do right now and never more. Eager revocation would mean hooking every path that can remove authority (membership removal, role downgrade, archive, org-role change) and missing one would leave a schedule firing with authority its owner no longer has. Runs are attributed to that owner because `runs.created_by` is NOT NULL: unattended work still names a human, which is what makes the check meaningful in the audit trail.

- **Project API keys (`Authorization: Bearer agr_<key>`)** — the programmatic surface the `api_keys` table has been waiting for since the first migration (M2 Track T). Project admins issue and revoke keys under **Settings → API keys**; the plaintext is shown exactly once and only a sha256 hash plus a 12-char lookup prefix is stored. Verification reuses the daemon-token shape — prefix-indexed lookup, constant-time compare — now extracted into one `bearer-tokens` module that the `agrd_` runtime tokens and invitation tokens call as well, replacing three near-identical copies. Unknown, malformed, revoked, and expired keys all answer the same `401 api_key_invalid`, so probing cannot mine the difference.

  Two decisions shape what a key can actually do. **Reach is an allow-list, not a denylist**: a table of (method, path) → required scope names every endpoint a key may touch (`tasks:write` to submit/retry/cancel, `runs:read` for tasks/runs/steps/checkpoints/comments/artifacts, `resources:read` for the catalog), and everything unlisted answers `403` — so an endpoint added tomorrow is unreachable by every key issued before it, and administration stays out of reach even for a key its org admin created (the org role is pinned to `org_member` on key requests regardless). **A key acts as its creating user and is bound to its project**, which keeps project membership the one source of access: revoke someone's membership and their keys stop with it. That binding is enforced inside `assertProjectRole`, which now takes the whole request principal rather than a bare user id, so the check cannot be skipped by forgetting it at one of the several call sites that reach a project through a loaded run or task. Audit-on-use falls out of the same change: mutations already wrote an audit row, and those rows now name `actor_api_key_id` alongside the user, so a leaked key is distinguishable from its owner working in the browser.

- **HSTS on TLS-terminated deployments (`AGRIPPA_HSTS_MAX_AGE`, default one year)** — the api now sends `Strict-Transport-Security` on requests whose proxy set `X-Forwarded-Proto: https`, so it stays inert until TLS actually terminates in front of the stack. The motivating case is a mainland-China host: a middlebox there intercepts plain HTTP naming a domain without an ICP filing (备案) and answers it with a block page (GB2312, titled 非法阻断), reading the domain from the **cleartext `Host` header**, which TLS encrypts — so `https://host:3000` serves while `http://host:3000` is intercepted on the same host and port, a split that looks like a blocked domain and tempts the wrong fix (a bare-IP origin, which forfeits the secure context that the admin copy buttons need, the cookie `Secure` flag protecting sessions and `agrd_`/`agr_` tokens, and IM card deep links — for a scheme that is intercepted anyway). A redirect cannot help, because the request is answered upstream and never arrives; HSTS acts on the client instead, having the browser rewrite bookmarked or pasted `http://` URLs before anything goes on the wire. `0` is a supported value, not "off": it emits `max-age=0` to clear a pin browsers already hold, which is the rollback path. Documented in design/08 and the operations manual (en + zh-CN), alongside a sharper `AGRIPPA_BASE_URL` note — it must equal the browser's origin exactly, port included, since better-auth derives both its trusted origin and its cookie `Secure` flag from it.

- **Executor-set job routing (M2 Phase A)** — run jobs now enqueue onto a queue named after the run's required executor set (`run.execute.<sorted ids>`, primary executor plus every agent-slot binding), and each worker consumes the queues that are subsets of its own registered executors via a manual fetch loop (`boss.work()` per subset queue would park fetched jobs invisible to capable peers), plus — since the engine always runs centrally even when execution is remote — the set queues covered by live daemon advertisements, refreshed each sweeper tick, so a daemon-only executor set always has an engine host. Runtime-derived queues are added only when no live central worker's executor set covers them (a coverable set is that capable worker's to poll; polling it everywhere would let an incapable worker fetch, route central, and decline in a sweeper-mediated steal loop) — where "live" is the same 150 s live-and-ready predicate routing's central preference uses (`consumers_ready_at` set, heartbeat within 2.5 beats), so a dead or boot-wedged sole-capable worker cannot suppress a live daemon's queues for the old 15-minute window. Daemon advertisements are treated as untrusted input: executor ids must be catalog members (each fresh pattern-valid id would mint persistent pg-boss queues fleet-wide — rotation has to be impossible, not just capped) and queue-name-safe, enforced at registration and re-filtered worker-side; oversized ads skip subset expansion and the total polled set is hard-capped as catalog-growth backstops — every bound logs what it dropped. A codex-requiring run can no longer land on a codex-less worker at all; the decline/`run.deferred` bounce path survives only for auth mismatches within the central fleet.
  - *Per-worker capability advertisement.* `worker_heartbeats` rows now carry the executors each worker constructed (with their env-auth providers) and the build version, written at boot and refreshed every beat. Submit gating reads per-worker sets from it: beyond the existing union availability check, a run whose executor set fits no single live worker is rejected at submit (`executor_unavailable`) — routed jobs go to one worker, so such a run could never be claimed. The codex advertisement also now recognizes an ordinary `codex login` (`~/.codex/auth.json`, honoring `CODEX_HOME`) as openai env auth — previously only explicit env keys counted, which would have hidden the primary daemon auth story.
  - *Fleet visibility.* A new **Admin → Workers** page (org-admin, `GET /fleet/workers`) lists every worker container with live/stale status (database-clock, 2.5× the heartbeat interval), its executor advertisement, consumer readiness, and build version, polling every 10 s — the per-worker health surface deferred since M1.6.

- **Remote runtime registry + daemon tokens (M2 Phase B, ADR-0017)** — the `runtimes` table gives bring-your-own-compute daemons durable identity: org admins issue `agrd_…` tokens from **Admin → Workers → Remote runtimes** (plaintext shown exactly once; sha256 hash + 12-char prefix at rest, constant-time verify, instant revoke), and daemons authenticate against the new `/api/daemon/*` sub-app — the codebase's first bearer auth, mounted outside the session gate with its own runtime principal, uniform `401 daemon_token_invalid` for every failure mode, and `audit_logs.actor_runtime_id` for daemon-actor rows. `register` records hostname/version/executor advertisement and returns protocol pacing hints; `heartbeat` bumps the liveness watermark routing will read.

- **Runtime-offline notifications (the Track N deferral)** — a remote runtime silent for 5 minutes appends a `runtime.offline` event to every running run pinned to it, flowing through the standard notification pipeline (per-endpoint dedupe, cards in both locales). The `notified_offline_at` watermark makes it one notification per outage: a runtime that recovers (is seen again) and dies again re-arms, but repeated sweeps of the same outage stay silent.

- **Publication inversion — `git.push` applies the approved patch to a pristine clone (M2 Phase B, ADR-0017 Decision 5; ADR-0011/0012 amended)** — the published tree now derives from the approved evidence bytes alone: `applyApprovedPatch` builds the deterministic snapshot commit in a pristine temp repo (base objects from the platform sidecar centrally, or fetched by the **server-pinned** base sha for daemon runs — resolved by `ls-remote` at checkout with annotated tags peeled to their commit, forced onto the daemon's clone, and with the daemon's own report demoted to a cross-check, so a daemon cannot smuggle an unreviewed base commit under a cleanly-applying patch) and pushes with a remote-ref CAS — an existing tip must *be* the deterministic commit or the publish refuses to overwrite. The SCM-layer drift re-check is retired (there is no workspace to compare; the engine-side approved-bytes selection still refuses refreshed evidence), `git.branch` no longer writes a sidecar ref and is a remote no-op (daemons materialize `runs.work_branch` from the dispatch payload), and the publishing-template routing exclusion is lifted — daemon-routed runs can now carry `git.branch`/`git.push` templates end-to-end with platform git credentials never leaving the server.

- **Compliance suite runs through the remote transport (M2 Phase B — the ADR-0017 acceptance gate)** — the FakeExecutor compliance suite and the agrippa/v2 suite now execute twice: in-process, and with every executor wrapped in `RemoteExecutor` driven by an in-process daemon loop against the real dispatch tables, introspecting the *same* fake instances. Green through both transports. The gate also flushed out a real bug: drizzle stores jsonb as a JSON-encoded string under this driver, so the claim path's raw-SQL reads (test loop AND the production `/api/daemon/claim` route) received a string payload — the daemon would have gotten `payload.executorId === undefined` on its first live dispatch. Both readers now parse the extra layer, with a route-level regression test.

- **`agrippa-daemon` — bring your own compute (M2 Phase B, the ADR-0017 headline)** — `bun run build:daemon` compiles a self-contained binary (`apps/daemon`; the Claude Agent SDK's JS is embedded while its native `claude` executable — a platform-specific optional dependency the compiler cannot bundle — is discovered from the machine's own Claude Code install (`claude` on `PATH` or `CLAUDE_CODE_EXECUTABLE`, found by the local binary smoke); Codex CLI detected from `PATH`) that registers with an `agrd_` token, long-polls `claim`, executes dispatches against a locally owned workspace (cloned with the **machine's own git credentials** — platform repo tokens never leave the server — and forced to the server-pinned base commit), resets agent-visible project config (`.claude`, `.mcp.json`) per dispatch exactly as the central worker does, materializes inline-shipped skill content under the payload's workspace-relative directory (the same layout the request's `localPath`s reference), streams sequence-numbered event batches with keepalives (abort honored within one interval), uploads artifact bytes before their events, and closes each dispatch with the canonical evidence snapshot — the exact `stagePlatformSnapshot` the worker runs, from the shared `@agrippa/workspace` package. `complete` means the stream ended cleanly (the step event carries the outcome); `fail` is transport-level death, which the server synthesizes into a typed retryable step failure. Setup is documented in the manual's operations page (en + zh-CN). The `ExecutionContext` contract also formally narrowed to `{ signal, logger }` per ADR-0017 Decision 2 — `usage` (a no-op) and `secrets` (an unconditional throw) were removed rather than transported.

- **RemoteExecutor + routing/affinity (M2 Phase B, ADR-0017 Decisions 2, 3, 7)** — the remote transport is an `Executor`: the engine binds daemon-routed slots to a proxy that writes a dispatch row, streams the daemon's events back in seq order, maps `ctx.signal` to the abort flag, rewrites artifact events to server-staged bytes, and converts a silent daemon into a typed retryable step failure via a 120 s deadman. Routing runs worker-side before engine construction — and therefore before the execution lease, so three guards close that window against concurrent deliveries: the affinity-pin write is a CAS whose loser adopts the persisted winner, the same CAS refuses to pin a leased run (a pin against a live lease is by definition a duplicate delivery poisoning the pin; row-lock ordering means no pin can land after a claim commits), and the engine awaits the consumer's pin verification as a `postClaim` gate — right after the claim, before any other initialization side effect, fail-closed: a moved pin or an inability to check drains with no trace (nothing finalizes) for a re-routed re-enqueue. Placement is also sticky: a started run with no pin executed centrally (remote always pins pre-claim) and stays central — migrating it to a later-appearing daemon would skip its succeeded checkout and run the remaining steps in an empty workspace — and the pin CAS itself requires `started_at IS NULL`, so a stale pre-execution snapshot cannot pin either. The engine hands out the control handle the moment the claim exists (before the verification gate), so lease renewal covers the whole initialization and SIGTERM drain reaches initializing runs. The `runs.runtime_id` affinity pin is absolute; the central-only strict rule keeps every run touching platform-held secrets (stored provider credentials — env- or project-policy — authed MCP servers, and `git.push` templates until publication inversion) on central workers, preserving ADR-0013's credential precedence; central workers are preferred only when one covers the executors **and** their env auth — scored per executor against each host's advertisement (a claude-implementer/codex-reviewer run needs anthropic on claude and openai on codex, not every provider on every executor), so a keyless central worker can no longer starve an authenticated daemon. The pin stays fail-closed after routing: a platform credential materializing for an already-pinned run (added while it was paused) fails the run typed (`provider_credential_unroutable`) instead of serializing to the daemon, platform-authed MCP servers report as missing resources, and the dispatch builder refuses any payload carrying provider auth outright. Submit gating now unions the org's live runtimes, making daemon-only executors submittable.

- **Dispatch protocol (M2 Phase B, ADR-0017 Decision 3)** — the daemon HTTP surface is complete: `claim` long-polls and atomically hands out the runtime's oldest pending dispatch (`FOR UPDATE SKIP LOCKED`; the abort piggyback rides every response), `events` accepts sequence-numbered batches deduplicated on `(dispatch, seq)` — at-least-once delivery that cannot double-count usage — with the abort flag on each response and empty batches as keepalives, `artifacts/:key` streams uploads into a per-dispatch staging area with the sha256 computed server-side at write time (daemon hashes are never trusted), and `complete`/`fail` are terminal CAS. `DiskArtifactStore` moved from the worker into `@agrippa/orchestration` (the api hosts the upload endpoint now, so compose mounts the artifacts volume read-write in the api container and the api image pins `ARTIFACT_STORAGE_ROOT` to the shared volume like the worker's — staging and adoption must read the same root across containers; the write surface is the token-gated endpoint alone) and gained the staging area plus a `staged` adoption source that re-hashes bytes on adoption.

- **Execution lease + real graceful drain (M2 Phase B, ADR-0017 Decision 4 / ADR-0009's deferred future work)** — claiming a run is now one CAS that moves it to `running` *and* takes a lease (`runs.lease_owner` = container id, 90 s TTL, renewed every 30 s). A second at-least-once delivery of a `running` run can no longer re-enter it (the old claim's self-transition tolerance allowed exactly that), and crashed `running` runs get a recovery path for the first time: the sweeper expires dead leases (one CAS-safe `run.lease_expired` event across replicas) and re-enqueues every leaseless running run. SIGTERM now actually drains: in-flight engines abort with reason `drained`, record their in-flight step as a crash (recovery attempt + executor-session resume apply on the next worker), release the lease **without finalizing**, and the worker re-enqueues immediately without burning retry budget — closing the gap where design/04 promised abort-on-drain but the worker only stopped the queue and killed steps mid-flight.

- **Outbound notifications (Track N of the M2 plan)** — a run that pauses for approval no longer waits for someone to have the inbox open: `checkpoint.required`, a new `checkpoint.expired` timeline event (expiry previously left no trace until the engine resumed), and every terminal state now fan out to per-project **notification endpoints** — a Feishu custom-bot card, a DingTalk robot card, or a generic JSON webhook signed `X-Agrippa-Signature: v1=hex(HMAC-SHA256(secret, "<ts>.<body>"))`. Cards render in the endpoint's own configured locale (a channel has no single recipient — amends the design/07 rule) and deep-link to the run via `AGRIPPA_BASE_URL`, which now reaches the worker in compose.
  - *Delivery bookkeeping is idempotent by construction.* Deliveries derive from `run_events` rows (written transactionally by the lifecycle) deduplicated per endpoint by a partial unique index; the sync runs post-commit, best-effort, at the four trigger sites (worker after `executeRun`, retry exhaustion, the approval-expiry handler, the API's direct cancel finalize) and enqueues a new `notification.deliver` pg-boss job per row (backoff, limit 5) — on an **`exclusive`-policy queue**, the one pg-boss policy whose singleton index spans created/retry/active (`standard` has no singleton index at all; `stately` keys its index by state, so a fresh job could bypass a retry backoff). An **activation watermark** (`activated_at`, reset by PATCH on re-enable and url/events changes, failing the endpoint's still-pending deliveries in the same transaction) keeps a new or materially changed endpoint from replaying history, and the worker claims each attempt by CAS before sending, so duplicate jobs cannot post concurrently or resend finalized rows. The reconciliation sweeper backfills missed events (24 h window), re-enqueues stale pending rows, and finalizes rows whose attempts were exhausted without bookkeeping. Zero engine changes — the compliance suite is untouched.
  - *Security posture matches provider credentials.* Signing secrets are write-only (`secrets` kind `webhook_secret`); endpoint routes are admin-only **including reads** — IM webhook URLs are capability URLs, so responses carry an unconditionally masked URL (no short-path exemption: a short path can be the whole token) and `hasSecret` only; per-kind host pins (open.feishu.cn / oapi.dingtalk.com) plus the same global-unicast DNS guard as provider endpoints, re-resolved at every send; **redirects are never followed** (a 307/308 would re-POST the signed body to an unvalidated destination) and at most 16 KiB of a receiver's response is ever read; changing a signed endpoint's URL requires re-entering the secret. IM success is judged by the response body's code, not HTTP status — both platforms answer 200 on errors.
  - *UI.* Project Settings gains a **Notifications** section: endpoint list with enable toggle and test-send, per-kind URL/secret hints, an event filter, and a recent-deliveries panel (10 s polling) with retry on failed rows. Every mutation is audited (`project.webhook.*`).

### Removed

- **The M2 deploy-skew shims** (post-flush cleanup): the legacy bare `run.execute` queue — workers no longer poll it, and a run whose executor set cannot be derived now fails the enqueue loudly instead of parking on a queue nobody consumes — and the deployment-wide `executor_registrations` table (migration `0022`, DROP-only) with its dual-write and submit-gating union fallback; per-worker heartbeat advertisements are the sole availability source.

Called from **both** `install.sh` (fail fast on a bad pin before creating users and databases) and `deploy.sh` (the only path an existing VM takes on update, so it is what gets the binary onto installs predating this release and what lands a `CODEX_VERSION` bump). Bun is deliberately not converged by `deploy.sh` — replacing the runtime under a live service should be an explicit `install.sh` re-run.

All optional — a keyless worker still registers `codex-cli`, and a project provider credential always outranks worker env (the whole protocol auth-var family is dropped before it is applied).

- **Documented that bubblewrap does not function under Docker** — the worker image has always installed it with a comment claiming it backs the SDK command sandbox, and under Docker's default profiles it silently never did. Measured on Ubuntu 24.04 / Docker 29: default seccomp blocks namespace creation; with `seccomp=unconfined` the namespace is created but mount setup fails without `CAP_SYS_ADMIN`. Restoring the inner sandbox costs both, dismantling the outer boundary to rebuild a weaker inner one — so the Compose posture is now stated explicitly: the container, the non-root `bun` user, root-owned `/app`, the throwaway workspace, and the subprocess env allow-list are the boundary. Use the VM/systemd topology where OS-level sandboxing is required.

- **SSE keepalive frames** — `GET /runs/:id/events` emitted nothing between events, so a run parked on a long agent turn or an approval looked like a dead connection to every intermediary: nginx cuts at `proxy_read_timeout` (60s default) and Cloudflare at ~100s. The stream now sends a comment frame every 15s (`AGRIPPA_SSE_KEEPALIVE_MS` to tune). Comment frames carry no `id:`, so they cannot disturb the `Last-Event-ID` cursor a client reconnects with. Previously the failure was survivable but noisy — EventSource reconnects and replays — now it doesn't happen. The knob is forwarded through compose and listed in both configuration tables, so it is actually settable.

- **`infra/deploy.sh` — a real deploy path for the Compose topology, with rollback.** The VM had `infra/vm/deploy.sh`; Docker had nothing, so updating meant remembering that `git pull && docker compose up -d` is *wrong here* — the SPA and API are baked into the api image, so it restarts the old code and reports success. The script always builds, tags images with the deployed commit (via the `AGRIPPA_VERSION` plumbing compose already had), waits on `/healthz`, and **rolls back to the previous tag** when the new one doesn't come up. Previously rollback was impossible at all: `build` overwrote `:latest` and left the prior image dangling and unnameable. A `flock` serializes concurrent deploys; only the current and previous tags are kept, since each pair is ~4 GB.

  The printed recovery drops and recreates the database rather than using `pg_restore --clean`, which only drops what the archive contains — tables a failed migration *added* would otherwise survive and can block the restore through dependencies; `--single-transaction --exit-on-error` makes a partial restore roll back instead of leaving a half-populated database. `HEALTH_TIMEOUT` is now a real wall-clock bound: it was counting only its own sleeps, so probe time (up to 10s each once a statement timeout was added) could push a nominal 180s past nine minutes. `infra/deploy.test.ts` covers the failure paths and the dump-retention cap with stubbed `docker` so they run in CI without a daemon — the script had none, and every property it asserts is one a review previously broke.
  Rollback aborts rather than continuing if it cannot restore the previous commit, since starting the old images against the failed commit's compose file is the mismatch that restore exists to prevent. The worker check bounds its database query with a connect and statement timeout, so a wedged Postgres fails within the health timeout instead of blocking past it.
  Pre-deploy dumps live in a `0700` directory with mode `0600`: they are a full copy of production, and the host also runs an unprivileged CI user that the deploy design treats as untrusted, so an inherited umask would have exposed them. The restore procedure is printed on **every** failure path — including the one where the rolled-back stack is also unhealthy, which is exactly when an irreversible migration is the cause — and it stops the app first, since `pg_restore --clean` cannot drop objects the api and worker still hold connections to.
  Images are tagged with the full commit SHA rather than a 7-char prefix, so a prefix collision cannot overwrite a tag that is someone's rollback target, and a stale `:latest` is pruned once it is no longer that target.
  Every compose invocation `deploy.sh` makes — including the worker readiness probe, which spells out `docker compose` because `timeout` needs a real command — and the restore procedure it prints on failure, names the project explicitly (`-p`); so does every command documented in the manuals — the procedure is pasted into a shell that does not share the deploy's environment, so without it the commands resolve against the tree's `name:` and act on the wrong stack. **Action required on upgrade:** `POSTGRES_PASSWORD` is now mandatory — a deployment that relied on the removed `agrippa` default must set that literal value, because Postgres applies this variable only when the data volume is first initialized and the existing role still has the old password. On the **first** upgrade to this release the previous release's `deploy.sh` is what runs — script changes take effect one deploy later — and it discards compose's stderr, so an unset `POSTGRES_PASSWORD` surfaces as `AGRIPPA_VERSION did not reach compose; images would be mistagged` rather than naming the variable. That deploy rolls back and your stack keeps running: set the variable and redeploy. Deploys from this release onward report the real cause. Setting anything else makes `DATABASE_URL` stop matching the role: the api fails authentication, health never comes up, and the rollback cannot recover it (`infra/env/.env` is untracked, so `git reset --hard` keeps the new value). Generate new passwords with `openssl rand -hex 24` — **not** base64, whose alphabet includes `/`, which terminates a URL's authority component and makes `DATABASE_URL` unparseable about 40% of the time. `createDb` now rejects an unparseable `DATABASE_URL` with a message naming the cause instead of failing opaquely at api boot, and `docs/manual/*/06-operations.md` carries a rotation recipe. The api healthcheck gained `start_period: 180s`, so boot-time migration and seeding no longer count as health failures. `POSTGRES_PASSWORD` now hard-fails like the two secrets beside it instead of defaulting to the literal `agrippa` published in the compose file, and `.env.example` ships it blank rather than as a placeholder that worked. The dev stack is named `agrippa-dev` (it resolved to `infra` — the production project name before it was pinned, with a volume also called `pgdata`) and binds postgres/redis to loopback rather than every interface. All four compose services are `restart: unless-stopped`, so a host reboot no longer leaves the instance down until someone runs a deploy. That is coupled to verification and must stay coupled: a crash-looping worker reports as running between restarts and registers its executors before it dies in consumer setup, so it would have satisfied both halves of the readiness check — `worker_ok()` now also fails when the workers' summed `RestartCount` moves during verification. It leaves the host checkout on a **detached HEAD** at the deployed commit: on a local branch every deploy force-moves that branch (the live host ended up with `main` pointing at the deploy tip and reported as ahead of a stale `origin` nobody fetches), and a stray `git pull` there would advance the tree past the running images — compose config, `.env` defaults and Dockerfiles are read from that tree, so manual compose commands would then use config that does not match what is running. It deploys **only commits reachable from `deploy`**: the script runs as root on the CI user's behalf, so an unconstrained argument would let its caller deploy any branch — including a compose file that mounts the host — and root-owning the tree would buy nothing. Verification covers both services (the api's compose healthcheck plus a fresh `executor_registrations` heartbeat), because a worker-only regression would otherwise deploy "successfully" and prune the image that worked. Rollback restores the previous commit's code *and config*, since re-upping old images against the failed commit's compose file is a mismatched state. It does **not** revert the database — the api migrates on boot before health is exposed and some migrations are irreversible — so a `pg_dump` is taken before every deploy and the exact restore command is printed on rollback rather than the schema being silently left behind.

- **`.janus/deploy.yml` — push to `deploy`, and the server updates itself.** A [Janus](https://github.com/hutusi/janus) pipeline running on the host calls `deploy.sh` with the exact triggering SHA, so a deploy applies the commit that triggered it rather than whatever the branch tip drifted to. Trigger is the `deploy` branch rather than `main`, because `main` takes doc-only commits and this is the only environment — going live is a deliberate fast-forward, and rolling back is moving the branch. Janus reaches root **not** through sudo: its own unit sets `NoNewPrivileges=true`, which every pipeline step inherits and no child can drop, so setuid is a permanent no-op there and `sudo` fails whatever the sudoers rule says. The pipeline instead starts a oneshot `agrippa-deploy@<sha>.service` with `systemctl start --wait` — D-Bus to pid 1 rather than in-process escalation, so the flag does not apply, and the deploy's exit status still reaches the pipeline. A polkit rule grants the janus user one verb (`start`) on one unit-name pattern. The deploy tree stays root-owned either way: a janus-writable tree plus a privileged `docker compose up` would let janus mount any host path as root, which would make the narrow grant worthless. Setup and the negative tests that prove the grant does not reach further are in `infra/janus/README.md`.

- **`.dockerignore`** — both images `COPY apps ./apps` / `COPY packages ./packages`, so every workspace `node_modules` in a developer's tree entered the build context and host-native binaries were layered into a Linux image. CI never caught it because it builds from a fresh checkout. Patterns are matched from the context root, so secrets and noise are listed in their `**/` form too: an unqualified `.env` would not have covered a git-ignored `apps/api/.env.local`.

- **Template format v3 — flat authoring format (ADR-0016)** — templates can now be authored in a flat, GitHub-Actions-style `version: 3` format with no `apiVersion`/`kind`/`metadata`/`spec` wrappers: top-level `slug`/`scenario`/`name`, `faber`-or-`slots` agent declaration, flat `skills`/`mcpServers`/`subagents`, `models` (no `.roles` wrapper), top-level `limits`, and `outputs` (no `.artifacts` wrapper). v3 is source-only — `normalizeV3ToCompiled` flattens it into the unchanged v2 IR (`CompiledTemplate`), so the engine, API, and DB are untouched; `compileTemplate` routes on `version: 3` before the existing `apiVersion` branches. Six builtins converted (`pm/status-report`, `pm/plan-breakdown`, `swdev/requirement-delivery`, `swdev/requirements-dev`, `test/test-plan`, `test/regression-verify`); `swdev/bug-localize-fix.yaml` is intentionally kept on v1 as the v1→v2 upgrade-path fixture. v1/v2 sources keep working; the bilingual template-authoring manual and `docs/design/02` now teach v3 first.

- **Custom model providers + merged Models&Providers UI (slice 2)** — a member can now use a custom provider (DeepSeek, a self-hosted gateway, any Anthropic/OpenAI-compatible endpoint) end-to-end, and provider config + model config live in one place at each layer:
  - *Data-driven provider catalog (P-S2-1/2).* The resolvable provider set moves from the `PROVIDER_CATALOG` code constant to a `provider_catalog` table. Builtins (anthropic/openai/dashscope) are seeded `org_id NULL`; customs are org_admin-created with a per-wire-protocol default endpoint, an auth policy, and a host allowlist. `models.provider` / `provider_credentials.provider` still match `provider_id`.
  - *Protocol-driven resolution (P-S2-2/3/4).* Executor candidate providers are derived by wire protocol from the catalog (`claude→anthropic`, `codex→openai`) instead of the hardcoded `providers` lists — the change that lets a custom Anthropic-compatible provider be resolved by the claude executor. `providerAuthPolicy`/`providerServesProtocol`/`providerDefaultBaseUrl` accept the merged catalog; `providerServesProtocol` now treats native providers (anthropic/openai) as serving their *own* protocol only. `resolveAgentBindings` and the runtime engine load the merged catalog and pass it through; executor-core is unchanged (a custom provider with an explicit credential baseUrl already resolved at runtime).
  - *Provider-catalog CRUD + ref validation (P-S2-5).* `GET/POST/PATCH/DELETE /provider-catalog` (org_admin) registers customs; builtins are immutable/non-deletable. `POST /models` and `POST /projects/:id/providers` validate the provider is an active catalog entry (`provider_not_in_catalog`), closing the free-text gap; baseUrl overrides validate against the catalog's host pins.
  - *Merged UI (P-S2-6/7).* Admin → Models & Providers unifies provider-catalog management with model registration; the model-create provider field is now a Select of active catalog entries. Project Settings merges Grants + Providers into a single Resources tab grouped by provider — each provider shows its credential state + inline key add/rotate/remove + that provider's model toggles. The preflight `?tab=` deep-link points at `resources`.
  - *End-to-end test* proves a registered `deepseek` provider + models + credential resolves through the claude executor and reports preflight ready. Compliance suite (41), core/executor-core, and provider-catalog CRUD suites all green.

- **Convention-over-configuration grants & submit preflight** — onboarding no longer requires understanding the full provider → credential → model → grant → tier chain by hand:
  - *Built-in resources auto-granted on project creation (P0-3).* A new project starts authorized to use every active built-in resource (active models, published skills, active fabri) — `POST /projects` inserts the grants inside its create transaction, so a project is never in a "zero grants" state. Org-scoped resources and MCP servers stay an explicit opt-in. A seed backfill brings pre-existing default-org projects to parity on the next boot (idempotent). Security is unchanged: a grant says a project *may* use a resource — granting a dashscope model is harmless without a credential, and resolution still requires one.
  - *Provider credential auto-grants its models (P0-2).* `POST /projects/:id/providers` now grants that provider's active built-in models inside the same transaction and returns `autoGrantedModels` (newly-inserted count) for the UI to surface — coupling the two previously-decoupled steps (Settings → Providers vs Settings → Grants). Idempotent; removing a credential does not revoke grants (the preflight flags the missing key instead).
  - *Submit-readiness preflight (P1-4).* New `GET /projects/:projectId/task-types/:id/preflight` (viewer-readable) runs the same resolution + resource-authorization paths submit uses but reports each dimension (models, provider credential, skills, mcp, repo) as a structured check instead of failing fast on the first. The SubmitTaskPage summary renders a ✅/❌ checklist with a "Configure" deep-link (`?tab=`) to the right settings tab for each failing item, so config gaps surface before the round-trip. Stays in lockstep with submit because it calls the real `resolveAgentBindings` + skill/MCP/repo grant logic — no parallel rules to drift.

- **GitCode as a repo-connection provider** ([ADR-0011 addendum](docs/adr/0011-codex-executor-and-platform-scm.md)) — `pr.open` can now create pull requests on gitcode.com, so requirement-delivery publishes there end-to-end (previously a gitcode URL either mis-routed to a GHES-style API under the hard-coded `github` provider, or push-only `generic-git` failed the required `open-pr` step):
  - *Gitee-style v5 adapter.* `POST /repos/{owner}/{repo}/pulls` with Bearer auth and `html_url` responses, API base `api.gitcode.com/api/v5` for gitcode.com and origin-relative elsewhere; duplicate recovery runs on any 4xx (GitCode's duplicate status is undocumented) by listing open PRs on the base branch and matching the head client-side.
  - *No migration.* `repo_connections.provider` is plain text — the enum is TypeScript-only — so the new value is a type-level change; the settings form gains a provider picker instead of hard-coding `github`, and the repo list shows each connection's provider.
  - *Review corrections.* GitCode pushes authenticate as the token's real account (`GET /api/v5/user` → `login:token` in the push URL, mirroring the official CLI, with an `x-access-token` fallback); repo-connection mutations gained API integration coverage (validation, token write-only, RBAC, provider-carrying audit rows); `scripts/smoke-gitcode.ts` is the env-gated manual live smoke; the provider select is programmatically labelled.

- **Per-project provider credentials (Aliyun Bailian/DashScope first)** — projects configure model-provider API keys in Settings → Providers instead of relying on worker env ([ADR-0013](docs/adr/0013-per-project-provider-credentials.md)):
  - *Generic credential store.* One `provider_credentials` row per (project, provider) with an optional endpoint override; the key lives encrypted in `secrets` (new kind `provider_api_key`), write-only through the API (reads expose `hasCredential` only), rotated in place, deleted together with its secret, audited on every mutation.
  - *Provider catalog.* `PROVIDER_CATALOG` in `@agrippa/core` declares per-wire-protocol default endpoints and an auth policy per provider — `dashscope` requires a project credential (no legitimate env fallback), `anthropic`/`openai` keep worker env as the deployment default. Qwen models (`qwen3.7-max/plus`, `qwen3.6-flash`) are seeded; claude-agent-sdk serves `dashscope` (claude-only for now — Codex CLI ≥0.122 removed the chat wire API Bailian's compatible mode speaks; ADR-0013 amendment).
  - *Executor injection, project wins.* The engine materializes the project's key fresh per step (decrypted in the worker, redactor-registered before use, so rotation applies at the next step) and executors overlay it by replacing the wire protocol's entire auth-var family — Bailian lands as bearer `ANTHROPIC_AUTH_TOKEN` + gateway URL on claude; explicit `openai` proxy overrides land as a synthesized `-c model_providers` entry with a per-run `CODEX_HOME` on codex (so ambient `auth.json` can't outrank the project key). Codex now registers on a CLI probe alone; env auth at boot is no longer required.
  - *Base-URL overrides are policy-checked, and endpoint + key travel together.* A credential's baseUrl is where the worker sends the decrypted key, so overrides must be https, carry no userinfo/query, point at a public DNS name (never an IP literal or localhost — and the worker requires every resolved address to be global-unicast at each step; for IPv6 that is allowlist-first from `2000::/3`, so unallocated space never passes), and stay within the provider's pinned hosts (dashscope → the exact API hosts + `.maas.aliyuncs.com`, excluding customer-controlled OSS bucket domains) — rejected as `base_url_invalid` otherwise. Permanent non-resolution is the same actionable configuration failure; transient resolver errors remain queue-retryable. Changing the endpoint requires re-entering the key in the same request, so an existing write-only key can never be redirected; clearing back to the catalog default needs no key.
  - *Role-scoped, single-provider slot resolution.* Slots resolve only the model roles their steps (and subagents) reference, and provider-constrained slots resolve all of them from one provider (credentialed provider first, then cheapest, deterministic) — a step's base URL is process-wide, so mixed-provider slots could never execute. A slot blocked only by a missing credential fails submission with the new `provider_credential_required` error — retries enforce the same gate through full re-resolution against current configuration (ADR-0014 superseded the original frozen-resolution re-check), and a credential deleted mid-run fails the run with the same code before the executor is invoked; demo/`fake` resolution is unchanged.
  - *Keyless workers defer instead of failing.* Executors advertise which providers their worker env can authenticate (`envAuthProviders`); a run whose providers neither a project credential nor the claiming worker's env covers is declined before any status transition (the existing `run.deferred` heterogeneous-fleet path), so it waits for a capable worker rather than burning mid-run. The decline applies only to the pre-claim states the worker can actually re-enqueue (`queued`/`waiting_approval`) — a crash-recovered running run proceeds and, if its auth is truly unusable (including an env-policy credential deleted after claim on a keyless worker), fails actionably per-step with `provider_credential_required` instead of a generic error. Preflight checks only credential-row/secret presence; endpoint validation and decryption happen after claim, where bad configuration fails actionably and infrastructure errors retry.

- **`gpt-5.6-sol` joins the seeded model catalog** — the first seeded OpenAI model that works under a ChatGPT-account Codex login (`CODEX_HOME`); the existing `gpt-*-codex` ids are API-key-only and the backend 400s them under account auth, which left ChatGPT-login deployments with no runnable reviewer model. Context window and pricing follow OpenAI's model catalog (1,050,000 tokens, $5.00/$30.00 per MTok); a new CONTRIBUTING recipe covers adding builtin models.

### Changed

- **Tokens are the unit of account — Agrippa tracks no money** ([ADR-0015](docs/adr/0015-tokens-as-the-unit-of-account.md)). Every dollar figure the product showed was an inference from a registry price table it could not keep accurate: list rates drift silently, Bailian tiers Qwen pricing by input length, and Codex under ChatGPT-account auth has no per-token price at all. Tokens come straight from the executor, so they replace money everywhere.
  - *Template format (breaking).* `spec.budgets` → `spec.limits`; `maxCostUsd` → `maxTokens`, per-phase caps likewise; `maxDurationMinutes` unchanged. Builtins converted once at 200 000 tokens per USD. Versions published before this keep working — `upgradeCompiledTemplate` normalizes a stored `spec.budgets` (duration cap survives, cost caps drop), so pinned runs don't break. A draft still written against `spec.budgets` now fails compilation instead of silently losing its cap.
  - *Vocabulary (breaking).* `BudgetMeter` → `UsageMeter`, `BudgetExceededError` → `UsageLimitExceededError`, `ExecutionContext.budget` → `.usage`, error code `budget_exceeded` → `usage_limit_exceeded`, run-detail "Budget" card → "Usage limits". Tokens count input + output, cache excluded — the same measure the quota gate uses.
  - *Model selection (breaking).* New `models.rank` (integer, lower wins, ties by model id) replaces price as the ordering key for both within-tier resolution and the cross-provider tie-break. Migration `0010` backfills it from the existing prices, so an upgraded deployment resolves as before wherever prices differed. The exception is equal-price rows, which previously resolved by unspecified row order (`fetchGrantedModels` has no `ORDER BY`): those now break deterministically by model id, so such a deployment can pick a different — but from here on stable — model.
  - *API (breaking).* `costUsd` is gone from `GET /projects/:id/usage`, `GET /runs/:id/steps`, and run payloads; `costLimitUsd` is gone from the quota endpoints; `POST/PATCH /models` take `rank` instead of the two price fields.
  - *UI.* Every visualization survives, re-based on tokens: "Daily spend" → daily tokens, "Spend by model" → tokens by model, the dashboard spend tile → tokens against the token quota, and the Usage page's second tile → remaining monthly headroom. `formatCost` is replaced by `formatTokens`/`formatTokensCompact`.
- **Task retry re-resolves against current configuration** ([ADR-0014](docs/adr/0014-retry-re-resolves-configuration.md)) — retry used to copy the previous run's frozen bindings verbatim, so a configuration failure (a model the auth mode can't serve, a revoked grant, a deleted credential) could never be healed by fixing the configuration and retrying: the retried run re-billed the whole pipeline from checkout and died identically. Retry is now a re-submission of the pinned task:
  - *Template version and params snapshot stay pinned; everything configuration-derived re-resolves.* Agent bindings, per-slot model resolution, the resource manifest, the budget, quota headroom, and repo-ref ownership all re-derive through the same helper submit uses — with unchanged configuration the result is deterministically identical, so transient-failure retries behave as before. Configuration that still cannot satisfy a slot fails fast at the endpoint with submit's error codes (now localized, including `executor_unavailable`), never mid-run.
  - *Submit-time agent overrides persist.* The `agents` slot overrides picked on the submit form land on `tasks.agent_overrides` (migration 0008) and re-apply at retry, so a deliberate executor choice survives re-resolution; tasks predating the column retry with template defaults.
  - *`assertResolutionCredentialed` is retired* — the narrow credential re-check (ADR-0013 amendment 1) is subsumed by the full resolution gate. Retry also gained submit's transactional insert and an audit payload naming the source run.
  - *The Retry button says what it does.* A confirm dialog states that the new run starts over from checkout under current configuration and re-asks earlier answers/approvals; rejections surface as localized toasts; the run-page actions are hidden from viewers, who could only collect a 403.
  - *Review-round corrections (ADR-0014 amendment).* Status is configuration too: disabled MCP servers, skills without an active version satisfying their range (new `skill_version_unavailable`, matching via a helper shared with the worker's materializer), and disabled default Fabri now fail resolution instead of the run. Concurrent retries serialize on the task row (the loser gets 409 `run_active`, not a unique-violation 500), and submit/retry audit rows commit inside their mutation's transaction. `repo_not_in_project` joins both locales' error catalogs (retry surfaces it in a toast when the original repo connection was deleted), and the admin manuals document the skill-version and disabled-MCP semantics.
- **`approvals` table → `checkpoints`** (data-preserving rename) with `kind`, `iteration`, and a structured `response`; `run_steps` and `artifacts` gain `iteration`; `runs` gain `agent_bindings` and `work_branch`; new `run_comments` table (migration `0005_requirement-delivery`). Engine events rename `approval.required/decided` → `checkpoint.required/decided` and add `loop.*`, `branch.*`, `pr.opened`, `comment.added`.
- **Demo mode hardening** — when `AGRIPPA_EXECUTOR=fake`, every agent slot binds to the demo executor (a demo install must never silently route a slot to a real, key-consuming engine), `AGRIPPA_SCM=fake` fabricates branch/push/PR, and the demo executor is loop-round-aware (questions/findings in round 1, clean in round 2) so the delivery workflow demos end-to-end without tokens.

- **Invite-only onboarding; self-registration closed** — `POST /api/auth/sign-up/*` is now guarded and returns `403 registration_closed` (localized). The only ways to join the org are the new bootstrap-admin script (`bun --env-file=../../.env.local apps/api/src/cli/bootstrap-admin.ts`, reads `AGRIPPA_BOOTSTRAP_EMAIL`/`PASSWORD`, idempotent, creates the first `org_admin`) and the invitation flow: `org_admin` calls `POST /api/v1/invitations` to get a one-time `?token=…` link (token stored hashed — sha256 — so a DB leak can't be replayed); the invitee opens `/accept-invite?token=…` (public, no session), sets name + password, and is created as `org_member` via direct `users`+`accounts` insert (`hashPassword` from `better-auth/crypto`), then signs in through the normal endpoint. `GET /api/v1/invitations` lists, `DELETE /api/v1/invitations/:id` revokes. New `invitations` table + migration `0004_invitations`. The SPA login page drops the sign-up mode; a new `/accept-invite` page and an Admin → Members invite-management page are added. No email infrastructure exists — invite links are returned to the admin to share out-of-band. The `user.create` first-user→admin hook is retained as a safety net but superseded by `bootstrap-admin`.
- **`APT_MIRROR` build arg for the worker image** — `infra/Dockerfile.worker` now accepts an optional `APT_MIRROR` build arg that swaps Debian apt to a closer mirror before `apt-get install` (the worker image needs git/ripgrep/bubblewrap). `docker-compose.yml` threads it through as `build.args.APT_MIRROR: ${APT_MIRROR:-}`, documented in `infra/env/.env.example`. No-op when unset; set `APT_MIRROR=https://mirrors.aliyun.com` (or similar) for hosts where `deb.debian.org` is slow or blocked.
- **A second Compose stack could overwrite production's rollback target.** `deploy.sh` scopes its Compose operations by project, but `STATE_DIR` — holding `last-good` and the `pgdump-*.dump` retention window — was a fixed path, so a drill or staging copy run under `COMPOSE_PROJECT_NAME` without also overriding it would write its own rollback target over production's and evict production's dumps. It now records which project owns the directory and refuses to run for any other, before taking the lock, the dump, or touching `last-good`; refusing rather than inventing a path, because an auto-derived directory starts empty and the first-deploy fallback would then adopt the *other* stack's image as its rollback target. That fallback is also project-scoped now, instead of inspecting a hardcoded `agrippa-api-1`. The deploy lock stays global on purpose: image tags carry no project name, so concurrent deploys of different stacks genuinely race on them.

- **`infra/deploy.sh` shipped source files the application could not read.** A script-wide `umask 077`, added to keep database dumps away from the untrusted `janus` user, also applied to `git reset --hard` — so every file a deploy *rewrote* landed `0600`. The image build copies those modes, `/app` is root-owned, and the containers run as non-root `bun`, so the api and worker crash-looped on `EACCES reading /app/packages/db/src/client.ts`. It was latent from the moment the umask was introduced: every earlier deploy changed only deploy tooling and docs, never a file under `apps/` or `packages/`. The umask is now `022` and set explicitly, so modes do not depend on the caller's environment; the dump keeps `0600` via a subshell scoped to the one redirect that writes it, and `$STATE_DIR` remains `0700` root-owned regardless.

### Removed

- **The money columns** (migration `0011`, irreversible): `token_usage.cost_usd`, `project_quotas.cost_limit_usd`, `models.input_cost_per_mtok`, `models.output_cost_per_mtok`, and `runs.budget` — the last a denormalized copy of limits whose authoritative source was always the pinned `template_versions.compiled` row. Token counts, quotas, and all rows are preserved. Two cosmetic leftovers, neither read by anything: runs that failed before the upgrade still render the raw code `budget_exceeded`, and their `usage_totals` jsonb still carries a `costUsd` key.

### Fixed

- **Cancelling a queued or `waiting_approval` run did nothing the user could see** — `POST /runs/:id/cancel` set `cancel_requested`, published on the run's control channel, and re-enqueued, but for a run no worker holds all three miss: the control channel has no subscriber yet, the enqueue is singleton-deduped against the submit-time job, and the flag alone leaves `status` unchanged, so the run-detail UI stayed on the old status until the worker happened to pick the run up. These states now finalize to `cancelled` directly via the same CAS `finalizeRun` path (with its terminal event pushed to SSE clients); the pending singleton job becomes a no-op when the worker picks it up. `running` runs keep the existing abort path. The run-detail cancel button now toasts on error like retry already did.
- **The Docker bootstrap fields in `infra/env/.env.example` could not work either** — that file defines no `DATABASE_URL` (compose synthesizes it from `POSTGRES_PASSWORD`), so running the script against it fails in `createDb()`, and the values were never forwarded to a container. The fields are gone; the comment now shows the `docker compose exec -e` flow. `infra/vm/env.example` is unaffected — the VM env file does carry `DATABASE_URL`, so the `--env-file` form is correct there.
- **Deploy tooling could lock an operator out of their own install** — three places still told operators the first signup becomes the org admin, which stopped being true when self-registration was closed (`POST /api/auth/sign-up/*` returns 403 `registration_closed`). `infra/vm/install.sh` printed it as its closing banner without ever mentioning the bootstrap step, and `CONTRIBUTING.md` repeated it. Both now show the `bootstrap-admin.ts` invocation with a prompted password. The VM banner passes `--env-file` explicitly, since the script runs outside the repo root; CONTRIBUTING's dev form needs none, because Bun loads `.env.local` from the working directory natively.
- **The documented Docker bootstrap-admin command never worked** — both locales of `06-operations.md` shipped `docker compose --env-file … run --rm api bun …/bootstrap-admin.ts`. Compose's `--env-file` feeds interpolation of the compose file, not container environment, and the api service's `environment:` map does not carry the bootstrap keys — so the script always exited 1 on "must be set". Replaced with the `exec -e` form (and a `read -s` prompt, to keep the admin password out of shell history and out of a long-lived container's environment).
- **Deployment doc drift** — `docs/design/08` claimed migrations run as an api entrypoint step (`bun run db:migrate`); they actually run in-process at the top of `apps/api/src/index.ts` before the listener opens, and no entrypoint script exists. It also documented a `WORKER_EGRESS_ALLOWLIST` variable that nothing implements, which could read as an outbound-network restriction being in force — now recorded as deferred work rather than configuration.
- **`APT_MIRROR` was documented in a form that broke the build** — the Dockerfile substitutes only the *host* in Debian's deb822 sources, but every comment and example gave it as a URL (`https://mirrors.aliyun.com`), producing `http://https//mirrors.aliyun.com/debian` and an apt that cannot resolve the host `https`. Every package install then failed. The build arg now strips a scheme and any path, so both forms work, and the docs say host.
- **The compose stack's volumes were named `infra_*`** — with no `name:` key the project name defaulted to the compose file's directory, so `pgdata`/`artifacts`/`workspaces` were created under an `infra` prefix: surprising when restoring a backup, and liable to collide with any other stack living in an `infra/` directory. Now pinned to `agrippa`. **Upgrading from `v0.2.0` or earlier requires a one-time volume migration** — otherwise `docker compose up -d` builds a second, empty stack beside the old one and collides on the published port. The documented procedure guards both ends. It refuses to copy into a non-empty target, because `docker volume create` succeeds silently on an existing volume and `cp -a` leaves destination-only files in place, so copying onto a started-then-abandoned stack would merge two Postgres clusters. And it preflights the sources, because Docker creates a missing named volume on the fly — a mistyped name would otherwise mount an empty one, copy nothing, and leave a fresh empty database that passes `/healthz` while the real data sits elsewhere. Step-by-step procedure: [Operations → Upgrading from a deployment created before the compose project was named](docs/manual/en/06-operations.md#upgrades--scaling).
- **`AGRIPPA_PORT` exposed the plain-HTTP API on `0.0.0.0`** — it is the left side of the compose port mapping, so it can carry an interface. Documented as `127.0.0.1:3000` for the reverse-proxy topology, which is the only supported way to run it publicly.
- **The worker could be SIGKILLed mid-drain** — it handles SIGTERM by awaiting pg-boss's graceful stop, but compose's default `stop_grace_period` is 10s. Raised to 60s.
- **A thorough review report could kill its run at the review gate** — checkpoint-driving artifacts (review reports, questions) had to fit the store's general 64 KB inline threshold, but the interaction schemas admit a valid report of ~248K characters (up to ~1.5 MB as escaped JSON), so a schema-valid report of a large change failed the run with `contract_violation` instead of opening the gate. Interaction artifacts now get their own inline allowance (`INTERACTION_ARTIFACT_MAX_BYTES`, 2 MiB), sized to dominate any schema-valid payload — so only genuinely invalid (or padded) content can still trip the distinct too-large error. Both previously-untested failure paths (store-time and the resume-time legacy-row backstop) are now covered by the engine compliance suite.
- **A working diff over 64 KB could no longer be published** — the `git.push` evidence check compared the fresh snapshot against `artifactValues`, which holds `""` for any patch artifact past the inline threshold, so every run whose reviewed diff exceeded 64 KB died at publish with a phantom "workspace changed after the reviewed evidence". Every stored artifact row now carries a store-time `sha256` (migration `0013`), and the check verifies a larger-than-inline patch against that digest — deliberately never against the spilled disk bytes, which live on a volume agent subprocesses can write to (same container, same user, no inner sandbox under Docker) and could be rewritten after review. File-kind artifacts hash the exact byte stream being written (single pass, size counted and capped mid-stream), not a re-read of the mutable source. Genuinely drifted workspaces still fail, and a spilled patch without a digest fails the push with a distinct `contract_violation` instead of publishing unverified. The digest is tamper-resistance within the documented deployment posture, not a boundary — an agent that recovers worker credentials (possible under compose, see the sandboxing residual in design 08) can forge database state wholesale; per-run isolation remains the M2 work. This was the remaining follow-up from PR #5's review rounds.
- **Deploy verification now proves each worker replica actually consumes, not just that one registered** (closes #15) — `worker_ok()` accepted a fresh `executor_registrations` row, which the worker writes *before* starting its pg-boss consumers, so a worker that registered and then wedged inside consumer setup read as a successful deploy while nothing consumed the queue. Workers now upsert a per-container row into the new `worker_heartbeats` table (migration `0012`) — hostname inside compose is the container id — where boot start clears `consumers_ready_at`, only the return of `boss.work()` for every consumer re-sets it (so a restart that wedges cannot coast on the previous boot's stamp), and the sweeper bumps a 60 s liveness heartbeat (rows silent for a week are pruned). `deploy.sh` requires one ready-and-alive row per expected `WORKER_REPLICAS`, scoped to the hostnames of this fleet's running containers (`docker inspect {{.Config.Hostname}}`) so a foreign container pointed at the same database — a debug `docker run`, an out-of-band scale leftover, a second stack — can never supply the count; aliveness uses a sliding 90 s window on the sweeper heartbeat (a fixed post-deploy stamp would let one beat mask a later wedge, and would fail rollbacks/same-commit redeploys that reuse unchanged healthy containers), the sweeper beats first in its tick so sweep errors cannot skip it, and `WORKER_REPLICAS` below 1 is rejected up front (0 made the check vacuous). The replica-count and RestartCount checks stay, each still catching what the row count cannot (out-of-band scaling; crash loops that get past consumer setup). Workers also **wait for the schema their own build expects** before writing anything (`awaitSchema` compares the image's migration journal against `drizzle.__drizzle_migrations`, up to 5 minutes), so a worker can no longer race the api's on-boot migration and crash-loop on a missing table — which would trip the RestartCount check on the very deploy that introduces one. The wait lives in the image rather than a compose `depends_on: api: service_healthy` on purpose: it also covers host reboots and `docker start` (restart policies ignore `depends_on`), the VM topology, and `AGRIPPA_MIGRATE_ON_BOOT=0` (where api health proves nothing about the schema), and it keeps `up -d` from blocking on another service's health — which would turn a crash-looping api into an unbounded deploy hang. `up -d` is bounded by `timeout 300` as a hung-daemon guard, sized so the worst path (up + verify + rollback's up + verify) still fits the deploy unit's `TimeoutStartSec`.

- **Dead clicks after confirming a retry, and sidebar collapse quirks** — Radix modal layers lock `<body>` with `pointer-events: none` while open; the retry confirm dialog navigating to the new run could unmount it mid-exit-animation and leave the lock behind, after which every click (the sidebar toggle included) silently did nothing:
  - *Stale body locks are cleared when a navigation settles* — a router subscription resets the lock, covering every dialog/dropdown that a route change can unmount mid-close.
  - *Sidebar state finally persists.* The vendored sidebar wrote its `sidebar_state` cookie but nothing read it back (shadcn's Next.js starter reads it server-side; this is a SPA) — `Shell` now feeds it into `defaultOpen`, so a collapse survives reloads.
  - *The invisible expand rail is clickable full-height* (the sidebar container now out-stacks the sticky topbar, whose z-tie previously deadened the rail's top ~56px), and *the mobile drawer opens at its intended 18rem* (the sheet's side-variant width classes out-specified the sidebar's plain width override).
  - *The desktop sidebar renders even when a browser extension injects a global `.hidden` rule.* Injected extension CSS is unlayered and out-cascades every `@layer`ed Tailwind utility, so the vendored sidebar's `hidden md:block` pattern computed `display: none` at every viewport — the sidebar never rendered and the toggle appeared dead (diagnosed live: `span.hidden` was `display: none` even on example.com). Responsive sidebar visibility now uses `max-*:hidden` variants, whose class names an injected `.hidden` cannot match. Review corrections: the navigation-settle lock cleanup skips while any Radix layer still owns the lock — lock-owning primitives (dialog, alert-dialog, sheet, dropdown-menu, select) now self-identify via `data-locks-body`, replacing a role allowlist that missed `listbox` — and both the cookie parsing and the stale-lock predicate are extracted, unit-tested helpers.

- **Codex failures now surface their real cause** — a live requirement-delivery run died with the useless "codex reported an error" while the backend had said exactly what was wrong ("The 'gpt-5.1-codex' model is not supported when using Codex with a ChatGPT account"):
  - *Error items carry `message`, not `text`.* codex-cli 0.145 puts error-item text in `message`; the mapper read only `text`, dropping the detail. It now reads both.
  - *Warnings no longer mask or fabricate failures.* The CLI emits non-fatal error items ("Model metadata … Defaulting to fallback") and then completes the turn fine; first-error-wins let that warning shadow the fatal `turn.failed`, and any recorded error failed the step even on a clean exit. Fatal stream errors (`turn.failed` / top-level `error`, JSON blobs unwrapped to the inner sentence) and the exit code now decide failure; item errors only refine the message, and a step that completed with a lone warning succeeds (logged, not failed).
  - *Silent deaths get a usable message.* `stderr ?? fallback` never fired (stderr is always a string), so a CLI that died quietly produced an empty error message; failure paths also now log stderr through the executor logger.
  - *The timeline shows the failure where it happened.* `step.failed` only flipped a red icon on the turn — the error text appeared solely in the run-level banner, and only once the whole run had failed (a retried-then-recovered attempt's message was never shown anywhere). Each attempt's turn now renders its own `code: message` detail inline.
- **Fourth review round (PR #5)** — the evidence boundary now excludes all agent-writable Git metadata:
  - *Platform Git owns a complete private gitdir and index.* Checkout gives the agent a copy of `.git` while the pristine original moves to a sibling sidecar. Evidence and publication rebuild the sidecar index from the trusted clone base and explicitly exclude `.claude`, `.mcp.json`, and `.agrippa`, so a config symlink/special file or agent edits to the index and `info/exclude` cannot alter the platform view. This supersedes the third round's config-restore design.
  - *Publication is one verified snapshot commit.* The platform compares stored and current patch evidence without truthiness shortcuts, treats Git failures as errors, refuses empty snapshots, stages once more inside the SCM operation, and publishes one idempotent Agrippa-authored commit whose tree matches the approved patch. Agent-local commits remain working checkpoints but are intentionally not preserved in the PR history (ADR-0012).
  - *Agent project configuration is invocation-scoped.* `.claude` and `.mcp.json` are removed without following symlinks before resource materialization and every agent attempt/resume, then only authorized skills are restored. Settings and hooks left by one agent cannot affect the next.
  - *Platform Git receives no model-provider credentials.* It now uses a system-only allow-list rather than the executor environment; hostile hooks/filters are still neutralized, and regression tests assert Anthropic/OpenAI/Codex keys never enter Git children.
- **CodeRabbit review pass (PR #5)** — the publish snapshot commit is now fully deterministic (author/committer dates pinned to the clone base, so any retry or racer reproduces the identical SHA — the `update-ref` CAS then chooses between equals); `request_changes` requires a non-empty comment at the schema level (the revision step interpolates it — the UI already enforced this, the API now does too); checkpoint panels keep working when the evidence preview fails to load (a retry button appears, sending findings back for fixing stays possible, while accepting/approving blind — including a partial fix's implicit waiver — stays blocked); "Accept all recommendations" can no longer submit an answer set missing required answers; the run timeline follows the live stream instead of auto-scrolling only on mount; `run.deferred` timeline entries show the concrete reason; plus test-correctness fixes (awaited `rejects` assertions, temp-dir cleanup) and doc alignment (executor diagram, loop-only request-changes, slot-interchangeability limits — both locales).
- **Third review round (PR #5)** — five fixes; the platform now trusts nothing an agent can write:
  - *Platform git no longer executes agent-controlled hooks with worker secrets.* Every platform git call (evidence diffs, the finalizing commit, the credentialed push) runs in a directory the agent could write — including `.git/**` — and used to inherit the worker's full environment. The `git()` wrapper now uses the executor allow-list env scrub (no `DATABASE_URL`/`AGRIPPA_SECRET_KEY`/provider keys reach any git child), disables global/system gitconfig and neutralizes `core.hooksPath`/`core.fsmonitor` on every call, and restores repo-local `.git/config` from a provision-time snapshot before diff/push — erasing agent-added filters, textconv drivers, `url.insteadOf` push redirection, and credential helpers. The snapshot and the clone-base SHA live in a per-run platform sidecar outside the agent-writable tree, which also stops an agent from moving `refs/agrippa/base` to blank the patch evidence. A hostile-workspace test drives the publish path with weaponized hooks, filters, and an `insteadOf` redirect and asserts none of it executes.
  - *Reviewers are read-only and drift refuses to publish.* v2 agent steps take a per-step `access:` override; the delivery template's review step declares `readOnly` (claude enforces it via the isolation seam, codex via `--sandbox read-only` with fenced-json artifact synthesis). The round-2 push-time evidence *refresh* is replaced by a hard failure: `git.push` fails the run (`contract_violation`) when the workspace no longer matches the stored patch — refreshed evidence is not approved evidence.
  - *Lost workspaces fail fast.* Workspaces are host-local; a resume landing on a worker host without the checkout now fails with `workspace_lost` instead of silently running every remaining step against an empty directory (re-provisioning would fabricate a workspace missing the work branch and all agent commits — deliberately not attempted).
  - *Duplicate interaction ids are rejected.* Questions and review findings are keyed by id everywhere downstream (answers, selections, waivers, React keys); the artifact schemas now reject duplicates.
  - *ADR hygiene.* ADR-0010's semantics correction is recorded as an appended amendment (the append-only rule applies even pre-merge), and ADR-0011 gains an addendum for the platform-git-distrust and read-only-reviewer decisions.
- **Second review round (PR #5)** — six fixes, four of them establishing one evidence contract: *the patch artifact a user approves and the pushed PR contain exactly the same changes, and the sanitized paths (`.claude`, `.mcp.json`, `.agrippa`) appear in neither, in either direction*:
  - *PRs can no longer silently delete sanitized repository files.* The round-1 sanitization `rm`'d repo-supplied `.claude`/`.mcp.json` and hid the deletions only from the diff — an agent's `git add -A && commit` still shipped them. Sanitized paths are now invisible to git itself: tracked entries get `--skip-worktree` before removal and the paths join `.git/info/exclude` (covering the *untracked* side, which the platform itself populates — materialized skills under `.claude/skills/`, artifact scratch under `.agrippa/`), so the diff's pathspec excludes are gone entirely and evidence and commits agree by construction.
  - *Patch evidence now equals the push.* `git.push` gains a platform finalizing commit for anything the agent left uncommitted (Agrippa identity, host gitconfig isolated), refuses to publish a branch with no commits and no changes ("nothing to publish" instead of a provider 422 later), and re-diffs at push time to detect post-review drift. (The refresh-and-publish behavior this round introduced was replaced in the third round: drift now fails the run.)
  - *`{}` no longer reads as a clean review.* The interaction artifact schemas are strict with required lists: a missing or typo'd `findings`/`questions` key previously parsed as an empty artifact (zod default + unknown-key stripping) and auto-passed the gate; it now fails the producing step. Auto-pass stays asymmetric by design: absent questions pass (nothing to ask), absent review reports fail (a gate without evidence never passes).
  - *Heterogeneous fleets defer instead of burning retries.* A worker picking up a run bound to an executor it didn't register now declines the job before any status transition (typed `ExecutorUnavailableError`), appends a `run.deferred` timeline event, and lets the reconciliation sweepers re-enqueue until a capable worker claims it; `running` runs still rethrow (execution lease remains future work).
  - *Work-branch suffixes widen from 32 to 48 random bits* (12 hex chars of the UUIDv7 tail) — ~1.2% birthday-collision odds at 10k runs was too high for a scheme `pr.open`'s duplicate-recovery depends on.
  - *Docs match the runtime again* — ADR-0010 and the design docs now state the asymmetric auto-pass semantics and the heterogeneous-worker recovery path.
- **Review-round hardening (PR #5 code-review findings)** — eight fixes, four of them blockers for the requirement-delivery workflow:
  - *Committed work no longer vanishes from patch artifacts.* Checkout pins the clone-time HEAD as `refs/agrippa/base` and `diff()` reports against it (committed + staged + worktree, with the sanitization deletions excluded); a required patch whose auto-diff comes back empty now fails the producing step retryably — before push/PR, not at end-of-flow. Also repairs the latent empty-patch bug in v1 `bug-localize-fix`. New real-git integration tests cover exactly the path the fake-workspace compliance fixtures could not.
  - *Malformed interaction artifacts no longer auto-pass their checkpoints.* Questions/review-report artifacts are validated against the shared schemas at store time (the producing step fails with `contract_violation`; template retry applies — the review step gains one), with a strict checkpoint-time backstop for resumed runs: an absent review report fails the run (a gate without evidence never passes), and over-inline-limit sources get a distinct error instead of reading as "no findings".
  - *Work branches are unique across tasks.* Run numbers restart per task, so the default branch name appends the run id's random tail (`agrippa/run-<n>-<shortId>`, exposed as `run.shortId` — the UUIDv7 *tail*; its head is timestamp bits).
  - *Submission rejects executors the deployment cannot run.* Workers advertise their registered executors in a heartbeated `executor_registrations` table (migration 0006); `resolveAgentBindings` rejects any resolved binding without a recent registration (`executor_unavailable`, checked before model resolution), and the submit page's picker disables unavailable engines. Heterogeneous workers can still race at pickup; the second review round above turns that into a deferral instead of burned retries.
  - *Checkpoint panels present the latest evidence.* The artifacts endpoint now orders rows and exposes `iteration`, and panels take the last row per key — after "request changes", responders can no longer approve the previous round's plan or patch.
  - *`pr.open` is idempotent across retries.* A GitHub 422 / GitLab 409 on the retry recovers the existing open PR by head/base (safe now that branches are unique) instead of failing a run whose PR exists.
  - *Codex cannot load undeclared capabilities.* `codex exec` runs with `--ignore-user-config` and `--ignore-rules` (auth still resolves from `CODEX_HOME`), and the boot probe refuses to register a CLI that lacks those flags — silently running without config isolation is the vulnerability.
  - *Question contracts are enforced end to end.* Select questions must carry options (a required optionless select was an unanswerable form — input checkpoints have no reject, so runs deadlocked until timeout), recommendations must match the question kind (booleans allowed), and the respond endpoint validates every answer against its snapshotted kind and options.

### Security

- **Executor isolation seam** — one enforceable place (`packages/executor-core/isolation.ts`) decides every tool call and scrubs the subprocess environment. Read-only workspaces now actually deny shell and confine writes to the artifact directory; read-write workspaces confine writes to the workspace with a boundary-safe check (the previous `startsWith` let a sibling `<workspace>-evil` path through, and `Bash` bypassed the check entirely). **Reads (Read/Grep/Glob) are confined to the workspace too**, so the agent can't read `/proc/self/environ`, another run's directory, or the shared artifact store. The SDK subprocess environment is **allow-listed** — only the SDK auth variables and a fixed set of system essentials pass through, so platform secrets, DSNs, and injection vectors like `NODE_OPTIONS` are all dropped — with the OS `sandbox` enabled where available (bubblewrap installed in the worker image), `strictMcpConfig`, and repo-supplied `.claude`/`.mcp.json` removed after checkout so a checked-out repository can't inject hooks or permission overrides. The worker image runs as a non-root user with `/app` kept root-owned.
- **Event-payload secret redaction** — known secret values (the provider key, resolved MCP tokens) are redacted from every event before it is persisted or streamed over SSE, so a secret the agent echoes into output can't leak through the timeline.
- **Artifact path containment** — artifact ingestion resolves sources through `realpath` and rejects any that escape the workspace, closing a symlink disclosure (e.g. `ln -s /proc/self/environ`) that could exfiltrate secrets or other runs' files through the download endpoint.
- **Known dev-only advisory, accepted:** `bun audit` reports GHSA-67mh-4wv8-2f99 (esbuild dev-server request forgery) against esbuild 0.18.20, pulled in transitively by `drizzle-kit` → the deprecated `@esbuild-kit/esm-loader` → `@esbuild-kit/core-utils`. It does **not** affect shipped code: `drizzle-kit` is a devDependency, and the advisory concerns an esbuild dev server that `drizzle-kit` never starts (it already ships `tsx`, leaving the `@esbuild-kit` path vestigial). `drizzle-kit` 0.31.10 is the latest release, so no upgrade resolves it, and Bun supports neither nested `overrides` nor nested `resolutions` — a *global* esbuild override would force Vite's and tsx's esbuild (0.28.1) down to 0.25.x and break both. Revisit when `drizzle-kit` drops `@esbuild-kit` or Bun gains scoped overrides.

Optional skills/MCP servers are now grant-checked: an authorized-resource manifest is pinned onto the run at submit (required grants enforced, optional resources included only when granted) and the worker resolves resources only from it, so a project without a grant can no longer receive the platform's global credential (e.g. the shared GitHub token).

- **Main-branch CI red on PR merges** — commitlint parsed the `Merge: … (#N)` merge-commit title as an invalid commit type, failing every post-merge push run (and skipping Test/Build with it). Merge subjects are now exempt from commitlint; the PR's own commits are still linted by the PR-range step.
- **Codex review findings** — approvals can no longer be decided before their presented artifacts load (Approve stays disabled on load failure while Reject remains available, and unproduced `present[]` keys render explicitly); archiving a project no longer redirects straight back into it (active-membership filtering + clearing the stored last-project id); the approvals inbox shows a retryable error instead of "nothing pending" during an outage; sidebar links close the mobile drawer; and the usage chart derives its day domain and month label from the database clock that groups the data, not the browser's.
- **PR review findings** — the run timeline shows the pinned phase plan on queued runs instead of "no steps"; usage's by-task-type grouping keys on task-type id (names can collide) and its empty check considers cost; Usage/RunDetail/TemplateEditor show a retryable error state instead of a blank page when their query terminally fails; icon-only controls gained aria-labels; template deprecation is conditional on the published status (race guard); and the screenshot harness no longer skips cleanup on failure (`process.exit` inside `try`), uses a per-run scratch database, and watches the login page for errors too.
- **Root `bun run dev`** — the one-command dev boot crashed api/worker with "DATABASE_URL is not set": `bun --filter` runs each workspace's dev script with the workspace as cwd, outside the repo-root `.env.local`'s automatic loading. The api/worker dev scripts now pass `--env-file=../../.env.local` (a silent no-op when the file doesn't exist, so shell-export workflows are unaffected; exports still take precedence).

- **Dev-mode sign-in through the Vite proxy** — better-auth trusts only its `baseURL` origin (`http://localhost:3000`), so auth POSTs from the dev SPA on `:5173` were rejected with 403 `INVALID_ORIGIN`. The dev proxy now rewrites the `Origin` header to the API's own, completing the same-origin simulation of the production deployment (ADR-0001) instead of loosening the API's origin check.
- **Crash recovery for no-retry steps** — a worker that died mid-step no longer silently skips (or spuriously fails) a step without template retries; the crashed attempt no longer consumes the retry budget, and the executor session is carried onto the recovery attempt so resume works.
- **Atomic run lifecycle** — one `finalizeRun` owns every terminal transition: a single transaction does the status CAS (requiring `cancel_requested = false` for a success, so a late cancel wins atomically), finishedAt/totals, and the terminal event. Both the engine and the worker's retry-exhaustion path use it, so a run is never half-finalized and a queued run whose setup threw transitions `queued → failed` (now legal) with a terminal event instead of stranding. Event sequence numbers come from an atomic per-run counter (`runs.next_event_seq`), and approval decisions are CAS on `pending` with the sweeper re-enqueuing any run left paused by a lost resume enqueue.
- **Quota accounting** — the engine now counts the same monthly window as the submit gate, excludes the run's own spend from the headroom it checks (no double-count on resume), re-reads project usage at each step boundary so concurrent runs can't jointly overspend, and restores per-phase spend on resume so per-phase budgets aren't reset by a crash.
- **Artifact output contract** — patch steps no longer hand-write the diff (the engine generates it from `git diff`); collected artifacts are validated against the step's declared keys/kinds and matched by exact filename; only the current step's own expected files are cleared before an attempt (never a recursive `rm` a `.agrippa -> /work` symlink could redirect at the shared store, and `.agrippa` is stripped at checkout); missing/empty sources don't create zero-byte rows; binary (`file`-kind) artifacts are stored byte-exact; and ingestion size-caps and streams files instead of buffering them whole.
- **Authorized resources** — `requires.skills` is validated by the compiler and enforced by the engine; `skills` resolution returns `{ resolved, missing }` like `mcpServers`, so an unavailable required skill fails the step and an unavailable optional one is skipped (rather than throwing). `scripts/backfill-manifest.ts` reconstructs the manifest for pre-migration runs from **project grants** (not the full template).
- **SSE live gap** — the events stream subscribes and *awaits* the subscription being live before replaying, and treats the bus purely as a **wake-up** that triggers an ordered Postgres replay — so the cursor advances contiguously and a dropped event can't be skipped past (even on `Last-Event-ID` reconnect) (ADR-0007).
- **Production Compose** — split into a worker-only `workspaces` volume and a shared `artifacts` volume; the `api` runs as the non-root `bun` user and mounts only `artifacts` (consistent ownership whichever service initializes it) and receives `AGRIPPA_EXECUTOR` (the API chooses the executor at submit).

## [0.1.0] — 2026-07-17

The M1 milestone: all three layers of the platform, working end to end.

### Added

- **Scenario layer** — three scenarios (project management, software development, test & verification) with six builtin task types; submission forms auto-generated from compiled template input schemas; bilingual (en / zh-CN) SPA with live run detail, approvals inbox, project settings, admin registries, and a template editor with dry-run validation.
